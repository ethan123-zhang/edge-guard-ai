# 哨兵管家 — 总体设计

> 项目全称：**基于异构边缘计算与端侧 LLM 的智能家庭迎宾与安防系统**
> 文档版本：v1.0（主线版）
> 适用范围：小比赛现场 Demo + 答辩

---

## 1. 项目定位

在住宅大门口部署一套边缘智能系统：

1. 用 **Jetson Nano** 做人脸识别，判断来人是**熟人**还是**陌生人**，并累计到访次数；
2. 当**家中无人**时，用 **鲁班猫5（RK3588）** 上的**端侧 LLM** 与来人进行**多轮对话**，问明来意，并明确告知"已为您转达"；
3. 对话过程中**拒绝一切越权请求**（要求开门、索要密码等）；
4. 对话结束后，把**结构化结果**（来人身份、来意摘要、到访次数、时间）推送给**家庭主人**，同时在本地归档。

**一句话概括**：给家门装一个"记得住人的、会说话的、有分寸的"门卫。

---

## 2. 本版本（主线）的边界

单人开发、闲暇时间、一个月周期。**范围必须明确写死**，否则做不完。

### 2.1 主线范围（本版本实现）

| 编号 | 功能 | 验收标准 |
|---|---|---|
| M1 | 人脸检测 + 识别 | 检测到人脸并输出身份 ID；已知人脸能匹配，未知人脸标记为陌生人 |
| M2 | 熟人 / 陌生人判定 | 匹配成功 → 熟人；失败 → 陌生人；输出置信度 |
| M3 | 到访记录与计数 | 写入 SQLite；同一人重复出现能合并为一次到访事件；能查"第几次来" |
| M4 | 家中有人/无人判定 | 手机端一个开关可远程切换；无人时系统进入迎宾模式 |
| M5 | 多轮对话 | 最多 3 轮；ASK → ASR → LLM → TTS 闭环；能问出来意 |
| M6 | 来意总结与告知 | 对话结束生成一句总结，并播报"已为您转达" |
| M7 | 越权请求拒绝 | 检测到开门/密码/身份冒充类请求 → 硬拒绝 + 记录 + 上报 |
| M8 | 上报主人 | 通过局域网 WebSocket 推送到主人端；断网时写入本地待发队列，恢复后补发 |
| M9 | 本地归档 | 到访事件（含对话全文）持久化在 RK3588 本地 SQLite |

### 2.2 明确不做（本版本）

| 功能 | 为什么不做 | 后续去向 |
|---|---|---|
| 活体检测 | 需调阈值且口罩场景互相干扰，调试成本高 | 毕设 |
| 毫米波雷达低功耗唤醒 | 需接硬件 + 驱动，集成成本 >> 演示价值 | 毕设 |
| 暴力行为检测 | 需动作识别模型 + 数据集，一个月做不出来 | 毕设；本版本可用"异常声音告警"替代 |
| 口罩专项优化 | 降级策略设计本身即可作为答辩内容 | 毕设 |
| 云端 MQTT 备用通道 | 依赖公网，教室环境不可控 | 毕设 |
| 唤醒词 | 人脸触发已足够，唤醒词调优性价比低 | 不做 |
| 门内按键 | 手机开关已能表达"有人/无人" | 毕设 |
| 停留时长统计、沉默离场 | 数据本就在流程里，但统计与展示耗时 | 毕设（低优先级） |

> **答辩说明**：以上"不做"的项目，在本文档第 6 节均有对应的**设计分析**，答辩时作为"已知局限 + 未来工作"讲述，不回避。

## 3. 系统架构

### 3.1 节点划分

| 节点 | 硬件 | 角色 | 承担的负载 |
|---|---|---|---|
| 视觉节点 | Jetson Nano B01（4GB） | **眼睛** | 视频采集、人脸检测、人脸识别、事件上报 |
| 对话节点 | 鲁班猫5 v1（RK3588） | **大脑** | ASR、LLM 对话、状态机、TTS、业务逻辑、数据库、上报主人 |
| 主人端 | 手机 / 电脑浏览器 | **观察者** | 接收推送、切换"有人/无人"、查看历史 |
| 感知（可选） | PIR 红外模块 | **触发器** | 检测有人接近 → 唤醒补光灯 |

**关键设计决策**：**所有业务逻辑集中在 RK3588（大脑），Jetson 只做"识别 + 发事件"**。
理由：单人开发，减少双机联调面积。Jetson 侧代码跑通后基本不再改动，开发精力集中在对话链路上。

### 3.2 数据流

```
                    ┌──────────────────────────────┐
                    │        Jetson Nano           │
   摄像头 ──────────▶│  人脸检测 → 人脸识别          │
                    │  (ROI 裁剪, 只处理中央区域)    │
                    └───────────────┬──────────────┘
                                    │ WebSocket
                                    │ {face_id, is_known, name, confidence, ts}
                                    ▼
                    ┌──────────────────────────────┐
                    │      鲁班猫5 (RK3588)         │
                    │                              │
                    │  ① 查库：这人第几次来？        │
                    │  ② 查状态:家中有人? ──────────┼──▶ 主人端(手机)
                    │     ├─ 有人 → 只记录，不打扰   │    "有人/无人"开关
                    │     └─ 无人 → 进入迎宾流程     │
                    │  ③ 迎宾: TTS问候 → 录音        │
                    │     → ASR → LLM(状态机) → TTS │
                    │     (循环, 最多3轮)            │
                    │  ④ 越权请求 → 硬拒绝 + 标记    │
                    │  ⑤ 总结来意 → 播报"已转达"     │
                    │  ⑥ 写 SQLite + 推送主人端 ─────┼──▶ 主人端(推送)
                    └───────────────┬──────────────┘
                                    │
                                    ▼
                    ┌──────────────────────────────┐
                    │  主人端 (手机/笔记本浏览器)    │
                    │  · 接收到访推送 + 越权告警     │
                    │  · 切换"家中有人/无人"         │
                    │  · 查看历史记录与对话全文      │
                    └──────────────────────────────┘
```

> **注意方向**：主人端与对话节点之间是**双向**的——主人端既能收到推送，也能下发"有人/无人"开关（`set_home_state`，见 `02-接口协议.md` 5.1 节）。

### 3.3 关键机制

**机制一：ROI 区域裁剪**
只对画面中央矩形区域做人脸检测。作用：避免教室里的观众、走动的人触发识别。ROI 坐标放在配置文件里，可现场调整。

**机制二：麦克风门控（防自问自答）**
TTS 播报期间，**强制关闭麦克风输入**，播报结束再打开。
作用：教室是混响环境，喇叭声音会被自己录进去，造成"系统自己跟自己对话"的死循环。这是成本最低、收益最高的保命措施。

**机制三：人脸事件去重**
同一个人短时间内重复出现，合并为同一次到访事件。
规则：**同一 face_id 在 10 分钟内的多次出现，视为同一次到访**。

**机制四：断网优先本地**
上报失败不阻塞主流程：事件先写 SQLite（标记 `pending`），后台重试推送，成功后标记 `sent`。
作用：现场网络抖动时系统仍可用，且数据不丢。

## 5. 技术选型与理由

| 项 | 选型 | 理由 |
|---|---|---|
| 人脸检测 | **OpenCV YuNet** | OpenCV 官方自带，`pip install opencv-python` 即有，零额外依赖，Nano 上可用 |
| 人脸识别 | **OpenCV SFace** | 同上；配套 YuNet 使用，不需装 insightface 全家桶（避开 Python 3.6 依赖地狱） |
| 加速（可选） | TensorRT | 仅在主线跑通且有富余时间时再做 |
| 通信 | **WebSocket + JSON** | 双向、低延迟、易调试；不用消息队列（单人项目不必要） |
| LLM | **Qwen3-0.6B**（RKLLM，W8A8） | 野火教程验证过：prefill 305 tok/s、生成 23.96 tok/s、内存 784MB |
| LLM 备选 | Qwen2.5-1.5B | 能力更强但延迟上升，视体感决定 |
| ASR | **sherpa-onnx** 或 whisper.cpp（CPU） | 本地离线，不依赖外网；**NPU 留给 LLM，不抢资源** |
| TTS | 轻量中文 TTS（CPU） | 本地离线 |
| 数据库 | **SQLite** | 单文件、零配置、够用 |
| 主人端 | 单页 HTML + WebSocket | 无需框架，浏览器直接打开 |

### 为什么坚持本地推理

现场是**教室 + 手机热点**，外网不可控。ASR/LLM/TTS 全部本地运行，保证断网仍可演示；同时"数据不出户"是答辩加分点。

## 6. 未实现功能的设计分析（答辩用）

以下内容本版本不实现，但已完成设计论证，作为答辩材料与后续方向。

### 6.1 活体检测

**方案**：Silent-Face-Anti-Spoofing（MiniFASNet），静默式（用户无需配合做动作），运算量低，适合 Jetson Nano。

**设计要点**：活体检测不通过 → 不做任何交互，直接告警，且**不参与身份判定**。

**已知问题**：口罩遮挡本身是攻击特征之一，会干扰活体判断。需专门测试"戴口罩活人"的通过率。

### 6.2 遮挡（口罩）下的降级策略

**核心观点**：遮挡场景下**不追求强行识别**，而是分层降级。

| 情况 | 处理 |
|---|---|
| 置信度高 | 正常识别 |
| 置信度中 + 检测到遮挡 | 不做身份判定，标记"疑似熟人"，提高对话礼貌等级，上报时提示主人 |
| 置信度低 | 判定陌生人，走标准流程 |
| 活体不通过 | 拒绝交互 + 告警 |

这是**安全设计理念**（宁可不确定，不可误判），比宣称高识别率更可信。

### 6.3 暴力行为检测（降级为异常事件告警）

**为什么不做完整版**：动作识别需专门模型 + 数据集 + 标注，一个月做不出来。

**本版本的可选替代**：**异常声音检测**——用麦克风的音频能量突变 + 持续时间判断（如持续高声、撞击声），触发告警。成本约为完整方案的 20%，能达到大部分演示效果。

**答辩表述**：不要宣称"暴力行为识别"。表述为"异常声音事件告警"，并说明完整动作识别是下一阶段工作。

### 6.4 分级唤醒与低功耗

**设计**：PIR/毫米波检测有人 → 唤醒补光灯 → 唤醒 Jetson 视觉 → 确认陌生人且家中无人 → 才唤醒 ASR/LLM。
平时 Jetson 与 ASR/LLM 处于休眠，只有低功耗感知模块常开。

**本版本**：不实现。在文档与答辩中作为设计论证 + 功耗对比测算呈现。

## 7. 风险与降级预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| RKLLM 模型转换失败/太慢 | 中 | 无端侧 LLM，核心亮点丢失 | 降级为云端 LLM API；或先用 Qwen3-0.6B 保证跑通再换 |
| Jetson 人脸识别跑不动 | 低 | 链路不通 | 降低分辨率、跳帧处理、缩小 ROI；极端情况先写死结果跑通链路 |
| 麦克风噪声导致 ASR 不可用 | **高** | 对话演示失败 | 换 USB 阵列麦 + 播报时门控 + 用按键/文字输入兜底演示 |
| 现场网络不通 | 中 | 上报失败 | 局域网直连为主；断网时本地缓存，演示时展示"数据不丢" |
| 现场光照导致识别失败 | 中 | 演示中断 | 补光灯 + 曝光锁定 + 现场可调阈值 + 演示模式 |
| ASR/TTS 延迟过大 | 中 | 对话卡顿 | 用更小模型；限制回答长度；预生成常见话术 |
| 时间不足 | **高** | 功能不全 | 第 3 周强制冻结功能，第 4 周只打磨 |
