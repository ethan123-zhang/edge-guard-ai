# TensorRT 引擎封装（2026-11-06）

## 目的与边界

把「engine 怎么加载、怎么喂、坏了怎么办」收进 `vision/trt_backend.py`，让生产侧只做一次二选一：能校验通过就用 TensorRT，否则回退原来的 CPU 路径。**默认仍不启用**——本轮只做封装与板端回归，没有接 `VisionService`。

## 设计

1. **哈希绑定（sidecar）**：engine 旁边必须有 `<engine>.json`（`sentinel/trt-engine@1`），记录 engine sha256、源模型 sha256、TensorRT 版本、fp16、输入 profile、输出形状。加载时四项全核对；任何一项对不上就抛 `BackendUnavailable`，由 `create_backend()` 记一行日志返回 `None`，调用方走 CPU。不允许"版本漂了但还能跑"。
2. **动态批量**：SFace 的 engine 按 `min=1 / opt=4 / max=8` 建 profile；`run()` 按实际输入数组形状 `set_binding_shape`，输出缓冲按实际形状复用/扩容。检测 engine 保持静态 320。
3. **只依赖 numpy**：`tensorrt` / `pycuda` 在函数内 import，PC 上 `import vision.trt_backend` 不会失败；没有 TensorRT 的机器上 `create_backend()` 返回 `None`。
4. **不碰 cv2**：检测解码、五点对齐留在调用方；封装只搬张量。

## 板端回归（40 采样帧，同一哈希视频）

| 指标 | CPU dnn | TensorRT 封装 | 结论 |
| --- | --- | --- | --- |
| 检出脸数 | 69 | 69 | 逐帧数量完全一致 |
| bbox 最大差 | — | 0.0001 px | 可忽略 |
| 特征余弦（69 张脸） | — | 最小 0.999979 / 中位 0.999987 | FP16 可接受 |
| 检测（含解码）/帧 | 83.8 ms | 45.9 ms | 1.8× |
| SFace 全部脸/帧 | 218.1 ms | 35.8 ms（批量） | 6.1× |

sidecar 校验、动态批量（1/2/4 张脸同 engine）、不可用回退都用真实 engine 跑通；`create_backend` 在 PC 上（无 tensorrt）返回 `None` 并有日志，由单测钉住。

## 关键发现：解码才是检测段的另一半

回归里检测「只快 1.8×」，不是 engine 慢，而是旧 `decode()` 每帧在纯 Python 里重建 5875 个先验框再做 NMS，约 **31 ms/帧**，把 GPU 收益吃掉一半。单独跑 engine 是 11.7 ms（与旧基准一致），解码 ~31 ms。**接生产前应把先验表预计算一次、解码 numpy 化**，否则 TRT 的端到端收益只有 1.8× 而不是 ~4.7×。

## 限制

- engine 与 TensorRT 版本、设备绑定；换板/升级 JetPack 必须重建，sidecar 会主动拦下。
- FP16 有 ~1e-2 的绝对差（SFace 余弦 0.99999），对阈值 0.363/0.45 都不构成影响，但每次换模型要重跑一次回归。
- 多脸批量只到 8；超过要分块。
- 生产接线（`VisionService` 选 backend、预热、板端单测）未做。
