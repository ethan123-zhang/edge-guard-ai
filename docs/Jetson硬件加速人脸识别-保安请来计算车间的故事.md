# Jetson 硬件加速人脸识别：保安请来了一间计算车间

> 接着《Jetson 人脸识别直觉课：一个新保安的上岗故事》往下讲。
>
> 本文依据仓库截至 2026 年 11 月 7 日的代码、配置和板端验收记录撰写。本次没有连接 Jetson 复测；“已经跑通”指已有记录证明跑通过，不表示此刻板上正在运行。
>
> 小明、保安和车间是教学角色；标明“实测”的数字来自项目记录，其余数字会注明是示意。

## 第一章：保安认识人了，却忙不过来

上一次，我们让一个新保安站在“哨兵管家”的门口。

他的工作流程已经很清楚：

```text
拿到画面
  ↓
YuNet 找脸，给出人脸框和五个关键点
  ↓
按关键点把脸摆正，裁成标准小图
  ↓
SFace 把小图变成一张有 128 个数字的“面孔名片”
  ↓
把名片和登记册比较，决定是否认识
  ↓
跟踪、关联、去重，决定是否上报到访事件
```

YuNet 是找脸的模型，SFace 是提取人脸特征的模型。它们承担的任务不同，但都有一个共同特点：内部需要做很多数值计算。

一天，小明和朋友一起走过门口。保安拿到一张画面，算了半天，等他处理完，下一张又来了。

“我能看懂，但我来不及看。”

这就是这次硬件加速要解决的问题。

**我们主要改变的是完成计算的方式和速度，身份判断仍然要依赖照片质量、模型特征和比较规则。**

## 第二章：办公室里有主管，隔壁还有一间车间

保安所在的 Jetson Nano，可以想成一座小工厂。

厂里有两类很重要的工作人员。

第一类是 **CPU**。你可以把它想成几位很灵活的主管：读文件、判断条件、管理登记册、安排流程、收发消息，他们都能做。

第二类是 **GPU**。你可以把它想成一间有许多计算工位的车间：特别适合把大量相似的计算同时铺开做。

这里的“同时”，就是**并行计算**。

比如，你要给一大堆表格做同一种计算。如果每一行都能独立处理，分给很多工位一起算，就有机会比少量工作人员依次处理更快。

实际 CPU 也有多核和向量运算能力，并非永远一项一项算；GPU 的工位也不是一个个独立的人。这是帮助理解分工的类比，不能直接用工位数量计算加速倍数。

你这次项目记录中的板子是 **Jetson Nano**，其 GPU 是带有 128 个 CUDA 核心的 Maxwell 架构 GPU。不能把其他 Jetson 型号的能力直接套到它身上。[硬件来源：NVIDIA Jetson Nano 产品资料](https://developer.nvidia.com/embedded/jetson-nano)

保安惊讶地问：“既然车间一直都在，之前为什么还这么慢？”

## 第三章：有车间，不代表订单已经送过去

厂长翻了翻之前的工作单，发现了一件事：

**以前主要是 CPU 在算，GPU 车间没有通过这条软件路径接到模型计算的订单。**

项目 11 月 6 日的检查记录显示，板上的 OpenCV 4.1.1 没有编入 CUDA 支持。当时用它的 `cv2.dnn` 跑神经网络，走的是 CPU 路径。

OpenCV 是处理图像的工具库。`cv2.dnn` 是其中运行神经网络的一套接口。

所以，“板子装着 GPU”和“这个接口正在使用 GPU”，中间还隔着一层软件连接。

你可以把它想成：隔壁确实有车间，但主管手里的订单系统没有连接那条生产线，订单最后仍留在办公室处理。

这也解释了为什么下面几句话不能互相替代：

- 安装了 CUDA：有了一套使用 NVIDIA GPU 计算的软件基础。
- 安装了 TensorRT：有了优化、执行神经网络的工具。
- 当前服务正在用 TensorRT：这次程序确实选中了这条加速路径。

前两条是准备条件，第三条才是这次订单实际交到了哪里。

项目当时已经有 CUDA 10.2 和 TensorRT 8.2.1。后来采用的办法，是把模型推理交给 TensorRT，从另一条路径使用 GPU，而不是先重编整套 OpenCV。[项目依据：Jetson TRT 加速评估](Jetson-TRT加速评估-2026-11-06.md)

## 第四章：GPU 为什么特别适合帮这位保安

保安拿起一张照片：“看一张脸，怎么会有那么多计算？”

我们把镜头拉近一点。

图像由像素组成。神经网络会反复读取这些数字，乘上一组已经学好的权重，再把结果组合起来。

其中常见的一类操作叫**卷积**。先把它理解成：拿一个小小的数字模板，在图像的许多位置做类似的计算，形成新的特征图。

为了看清“类似计算”是什么，下面只用一个很小的示意：

```text
位置甲：像素甲1 × 权重1 + 像素甲2 × 权重2 + ……
位置乙：像素乙1 × 权重1 + 像素乙2 × 权重2 + ……
位置丙：像素丙1 × 权重1 + 像素丙2 × 权重2 + ……
```

这不是完整 YuNet 或 SFace 的公式，只是展示它们内部一类计算的形状。

关键在于：同一层里，很多位置或通道的计算可以并行安排。GPU 不必理解“小明是谁”，只要高效地完成这些乘法、加法等操作。

一层得到结果，再交给下一层。越往后，模型把输入逐步变成完成任务所需的表示。

在 YuNet 里，最后的输出用于恢复人脸位置、关键点和分数。

在 SFace 里，最后得到那张用于比较身份的 128 维“面孔名片”。

保安点点头：“所以 GPU 并不是另一位认识小明的保安。它是帮模型快速完成计算的车间。”

对。**模型决定怎样从图像计算出结果，GPU 提供适合这些计算的硬件。**

## 第五章：TensorRT 是车间的工艺师

车间有了，厂长又请来一位工艺师，叫 **TensorRT**。

工艺师问：“你们现在拿什么描述这套计算？”

保安拿出两个文件：YuNet 的 ONNX 模型和 SFace 的 ONNX 模型。

**ONNX** 是一种描述神经网络的通用格式，里面包含网络结构及参数等信息。你可以把它想成一份说明“有哪些步骤、怎样连接、用哪些权重”的计算图纸。

图纸可以交给不同的执行工具，因此同一个 ONNX 模型既可能被 CPU 路径执行，也可能交给 TensorRT。

**ONNX 本身不是硬件加速开关。**

TensorRT 看过图纸后，会为目标设备安排更合适的执行方案。例如，为操作选择合适的实现，在条件允许时融合相邻操作，减少中间结果搬运，并规划运行所需的内存。

这些是 TensorRT 的优化机制；我们并没有逐层检查本项目最终采用了哪些融合，不能把所有机制都当成这次加速倍数的已证实来源。[机制来源：NVIDIA TensorRT 性能优化文档](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/optimization.html)

安排完成后，生成的产物叫 **engine**，可以理解成“为这套设备和运行环境准备好的执行计划”。

在项目里，你会看到这两个名字：

```text
yunet_fp16.engine        → 执行找脸模型
sface_batch_fp16.engine  → 执行人脸特征模型，支持一定范围的批量输入
```

三者的关系可以这样记：

| 对象 | 工厂里的角色 | 真实作用 |
| --- | --- | --- |
| ONNX 模型 | 通用计算图纸 | 描述网络结构和参数 |
| TensorRT | 工艺师及执行系统 | 优化网络、构建和运行 engine |
| engine | 针对设备准备的执行计划 | 保存优化后的网络执行信息 |
| CUDA | 使用 GPU 的基础工具和执行环境 | 支撑 GPU 运算、内存管理等 |
| GPU | 计算车间 | 真正执行大量并行计算 |

我们的 Python 封装还用到了 **PyCUDA**：可以理解成让 Python 管理 CUDA 缓冲区、数据传递等工作的桥梁。

保安仍然负责整套流程，但最重的两段模型计算终于能交给车间。

## 第六章：FP16 是什么，难道照片少了一半？

保安看着文件名里的 `fp16`，有些担心：“照片是不是被砍掉了一半？”

工艺师笑了：“这是数字表示方式，不是把脸切掉一半。”

**FP32** 和 **FP16** 都是浮点数格式，分别使用 32 位和 16 位来表示一个数字。FP16 的表示更紧凑，但精度和可表示范围也更有限。

你可以把它想成计算时使用不同精细程度的刻度尺。粗一些的刻度可能已经足够完成某项任务，但也可能在敏感位置带来不可接受的误差。

在硬件和操作支持时，使用 FP16 可以降低部分存储和数据传输成本，并提高计算效率。实际能快多少，取决于设备、网络及执行方案。

**启用 FP16 也不等于网络每个操作都必须是 FP16。** 支持混合精度的执行方案可以保留部分操作的其他精度。文件名写着 FP16，不能代替逐层检查。

同样，TensorRT 是软件工具；它的名字不意味着设备必然有 Tensor Core。Jetson Nano 的 Maxwell GPU 不能按较新 Jetson 的 Tensor Core 能力来理解。

这一节只需抓住：**FP16 是计算精度的选择，能否使用以及是否值得使用，最终要看速度和结果两方面的实测。** TensorRT 的支持能力也随版本变化，不能把新版所有精度选项当成本板旧版本都支持。[参考：NVIDIA TensorRT 文档](https://docs.nvidia.com/deeplearning/tensorrt/latest/index.html)

## 第七章：速度快了，面孔名片会不会变样

保安问：“如果换了计算方式，还用了 FP16，会不会把小明算成小王？”

工艺师没有保证“绝对一样”，而是拿来同一批照片做对照。

项目 11 月 7 日记录的对照，是同一段固定视频采样 40 帧，比较 CPU 和 TensorRT 两条路径，检测分数门槛相同，都是 0.6。

实测结果如下：

| 检查项 | CPU 与 TensorRT 对比结果 |
| --- | --- |
| 检出人脸总数 | 79 对 79 |
| 人脸数量不一致的帧 | 0 / 40 |
| 浮点人脸框坐标最大绝对差 | 0.0001 像素 |
| 对应人脸特征的余弦相似度 | 最小 0.999978，中位 0.999986 |

这里的最后一项，是**同一张脸分别经 CPU 和 TensorRT 计算后，两份特征有多接近**。

它不是“身份识别准确率 99.9978%”，也不是在证明“小明和小王永远不会混淆”。

这份对照支持的结论是：**在这批测试输入上，换成 TensorRT 后，检测和特征结果保持了很高的一致性。**

如果有一个身份比较分数正好贴着判断阈值，很小的数值变化仍可能改变是否过线。换更多人、更多姿态、更多光照，还需要继续验证。[原始证据：板端管线对照 JSON](data/pipeline-board-check-2026-11-07.json)

## 第八章：两个人来了，为什么可以一起做名片

第二天，小明和朋友并排出现。

以前，CPU 路径要先给小明做名片，再给朋友做名片。

现在，保安先把这一帧里需要处理的脸收齐，每张都对齐成 112×112 的小图，再一起交给 SFace 车间。

这叫 **batch，批量处理**。

你可以把它想成：同一辆运输车一次带几件货，减少重复发车，并让车间有机会更充分地工作。但每件货仍然独立加工，结果还必须放回正确的人脸位置。

**批量不是把几张脸混成一张，也不是把几个人的特征平均。** 两张脸输入，应该得到两份对应的特征。

项目这份 SFace engine 支持的批量范围是 1～8。更多脸会分成若干批次处理，而不是硬塞进去。

还有一个值得讲的真实插曲：项目在板上的 OpenCV 4.1.1 CPU 路径实测到，SFace 批量前向会产生错误的重复特征。因此当前实现把 CPU 路径限制成每次 1 张；TensorRT 路径才保留最多 8 张的批量能力。

这不是所有 OpenCV 版本的通用结论，而是本项目对这套板端组合的处理。[实现依据：ONNX 管线](../vision/onnx_pipeline.py)

批量因此带来一个很实际的收益：同一帧已经有多张脸时，可以一起提特征。本项目并没有为了凑满 8 张而故意等未来几帧送来新人。

## 第九章：车间快了，为什么整条流水线还会慢

GPU 车间交卷很快，可保安仍然觉得有一段在卡。

厂长一查，发现办公室有位员工，每收到一张画面，就重新抄一遍同样的 5875 行表格。

这张表就是 YuNet 解码要用的**先验框表**。

“先验框”可以先理解成模型输出所参照的一组候选位置和尺寸。神经网络给出偏移、分数等数字后，**解码器**要按约定把它们还原为能画在图上的框和关键点。

解码之后，还要处理“同一张脸附近出现多个重叠候选框”的情况。这里使用的 **NMS**，就是根据分数和重叠程度筛掉部分重复候选框。

在固定输入尺寸的这条路径里，先验表本来不会每帧变化。项目于是把它改为模块加载时算好、以后复用。

11 月 7 日板端固定视频对照的实测：

```text
解码耗时中位数：32.689 ms → 0.799 ms
40 帧解码输出：逐位完全相同
```

这一段提速来自 **CPU 侧减少重复工作**，并不是 GPU 又多算了一段。[证据：解码先验预计算](解码先验预计算-2026-11-07.md)

于是，“硬件加速”的故事里多了一个重要转折：

> 让重计算交给 GPU，还要避免其他环节拖住整条流水线。

当前链路中，图像整理、解码、对齐、特征比较、跟踪关联、事件处理仍有 CPU 工作。数据交给 GPU、结果取回来也有成本。

Jetson 是集成式设备，CPU 和 GPU 共享物理内存体系；“送到车间”是类比，不代表跨越一块独立显卡。不过，本项目封装确实有主机侧与 CUDA 缓冲区之间的拷贝、执行及同步操作，不能因此把这些成本当成零。

所以单测 engine 的计算时间，往往小于整段服务处理时间。计时是否包含拷贝、解码、多张脸、事件逻辑，必须说清楚。

## 第十章：现在到底快了多少

保安终于问到了最关心的问题：“我上班时，到底能快多少？”

我们优先看接进真实 `VisionService` 的同组测试，而不是把不同日期、不同口径的最快数字拼起来。

11 月 7 日，固定视频采样 40 帧，在登记了 1 人的人脸库条件下，记录如下：

| 指标 | CPU 裸 ONNX 路径 | TensorRT 路径 |
| --- | ---: | ---: |
| 平均单帧推理耗时 | 270.96 ms | 56.32 ms |
| 记录的处理帧率 | 3.69 fps | 17.65 fps |
| 本地事件数 | 4 | 4 |
| 已知 / 陌生事件数 | 2 / 2 | 2 / 2 |

可以把它读成：这组视频测试里，完成一帧推理所需的时间从大约 0.27 秒，降到了大约 0.056 秒。

按推理耗时计算，速度约提升为原来的：

```text
270.96 ÷ 56.32 ≈ 4.8 倍
```

这里的 4.8 倍是**这组条件下的整条推理处理收益**。它同时包含换用 TensorRT、GPU 执行以及识别批量策略等影响，不能说是 FP16 单独带来的。

帧率和平均推理耗时也不必严格互为倒数：帧率还可能计入读帧和外围工作，统计区间也可能不同。不要硬把不同统计项凑成完全相等。

上述结果是已有的板端视频测试，不是对实时摄像头固定帧率的承诺。当时记录中板上没有 `/dev/video*`，实时摄像头从曝光、采集到事件送达的总延迟尚未验收。

关联层接线后的另一轮短视频入口记录约为 15.8 fps，也说明完整运行条件变化时，数字会变。实际速度还受脸数、温度、功耗模式和消息发送状态等影响。[原始证据：服务测试 JSON](data/service-smoke-2026-11-07.json)、[后续关联层板端验收](P2.5-关联层接线-2026-11-07.md)

## 第十一章：为什么有的记录说“没启用”，现在却说“用上了”

保安翻出昨天的交接：“这里明明写着默认未启用，怎么今天又说接上了？”

厂长拿出时间表：

| 阶段 | 做到了什么 |
| --- | --- |
| 11 月 6 日评估 | 证明模型能用 TensorRT 加速，并做了封装；当时尚未接入默认服务路径 |
| 11 月 7 日 P0 | 先优化 CPU 解码，减少固定表格的重复构建 |
| 11 月 7 日 P1 | 将 YuNet、对齐、SFace 新管线接进服务，板端 `board` 配置改为 `auto` |
| 11 月 7 日 P2.5 | 接入关联层，加入后端自检和心跳信息，记录实际是否使用 TensorRT |

所以早期交接并没有凭空失效，它描述的是更早的阶段。解释“现在”时，需要继续往后读代码和验收。

还有两件事发生在同一轮工作里，容易混在一起：

**第一件是把识别链路接通。** 板上 OpenCV 4.1.1 缺少 `FaceDetectorYN`、`FaceRecognizerSF` 这些便捷接口，之前服务路径主要依赖 Haar 检测，缺少给 SFace 做对齐所需的关键点。新管线自己连接 YuNet 解码、五点对齐与 SFace，补齐了这条路。

**第二件是让同一条新管线算得快。** 具备 ONNX 运行能力后，还可以选择 CPU 执行或 TensorRT 执行；前者能完成工作，后者在当前测试里明显更快。

因此，“现在能认人”与“现在认人更快”有关联，但原因不能只压缩成一句“打开 GPU 就行了”。[依据：P1 管线接线与验收](P1-ONNX管线接线-2026-11-07.md)

## 第十二章：怎么知道今天的订单真送去了车间

工艺师提醒：“配置写了优先使用车间，不等于每次启动都成功用上车间。”

当前仓库的 `vision/config/board.yaml` 使用：

```yaml
runtime:
  backend: auto
```

`auto` 的意思是尝试使用 TensorRT；某个组件的 engine 不可用时，该组件可以回退到 CPU dnn。因此，检测和识别可能都用 GPU，也可能出现一段 GPU、一段 CPU。

主要选项如下：

| 配置值 | 含义 |
| --- | --- |
| `auto` | 优先使用 TensorRT，加载不可用时按规则回退并记日志 |
| `trt` | 要求 TensorRT；不满足就启动报错，避免以为加速成功 |
| `cpu` | 新 ONNX 管线走 CPU，适合做对照 |
| `legacy` | 走原有检测、识别工厂路径 |

这里讲的是启动选择和加载失败时的回退，不能理解成任何运行时故障都保证自动恢复。

engine 旁边还有一份 **sidecar**，可以理解成“随行校验单”。当前封装会核对模型、engine 的哈希及 TensorRT 版本等信息。

**哈希**就像文件内容的指纹，用于发现模型或 engine 被换过；它不是人脸特征，也不是身份相似度。

engine 通常依赖构建时的设备和软件环境，不能当成到处通用的 ONNX 文件。换设备或升级环境，应重新构建、验证；校验单也不等于已经检查了全部硬件兼容条件。

项目提供了一个自检入口。在板端项目目录中，可以运行：

```bash
OPENBLAS_CORETYPE=ARMV8 python3 scripts/check_backend.py --profile board
```

这个命令会加载配置、创建并预热管线，检查检测和识别的实际后端；它不启动持续摄像头采集。

`OPENBLAS_CORETYPE=ARMV8` 是该板记录里所需的数值库环境设置，它本身不会开启 GPU。

成功时，关键输出应包含：

```text
yunet-onnx/tensorrt + sface-onnx/tensorrt
```

分别表示“检测使用 TensorRT”和“特征提取使用 TensorRT”。默认要求两者都满足，退出码为 0 才通过。

注意使用的是 `--profile board`。仓库还保留着旧的 `jetson_local` 配置，那份配置仍是 Haar 检测、关闭身份识别。仅仅在 Jetson 上运行，不会自动替你选对档位。[配置依据](../vision/config/board.yaml)、[自检脚本](../scripts/check_backend.py)

## 第十三章：保安算得快了，还是会犹豫

傍晚，小明低着头，逆着光走来。

GPU 很快做完了名片，保安却仍然说：“这次证据不足。”

你问：“不是已经加速了吗？”

保安说：“加速让我更早拿到结果，但这张照片本身就不容易认。”

硬件加速不会自动补出被遮住的脸，不会自动选好身份阈值，也不会自动修好跟踪和重复上报规则。

它可以为多看几帧、降低积压留出时间，但能否把这些时间转化为更可靠的结果，还要看系统怎样使用新证据。

比如项目的匿名关联夹具回放，后续记录从 12 条事件降到了 3 条，仍未达到期望的 2 条。这个问题属于“怎样判断是否同一次在场”，不能用“TensorRT 很快”来证明已经解决。[依据：关联层验收](P2.5-关联层接线-2026-11-07.md)

故事最后，保安重新排好了工作：

```text
CPU 整理画面
  ↓
TensorRT 调用 GPU 执行 YuNet：得到检测原始输出
  ↓
CPU 解码、筛框、根据五点对齐人脸
  ↓
TensorRT 调用 GPU 批量执行 SFace：得到人脸特征
  ↓
CPU 比较特征、跟踪关联、组织事件
```

这就是你项目里“Jetson 已经能使用硬件加速人脸识别”的具体含义：**原本让 CPU 承担的两段神经网络计算，现在有了经过验证的 TensorRT/GPU 执行路径，而且已经接进服务；CPU 继续负责前后衔接和业务判断。**

下次再看到 YuNet、ONNX、TensorRT、engine、CUDA、FP16、SFace，你就可以沿着这张工作单理解它们：谁定义计算，谁安排计算，谁真正执行，以及结果最后交给谁作判断。
