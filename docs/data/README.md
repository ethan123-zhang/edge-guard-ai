## 3. 与参考值对比

| 指标 | 我们实测 | 野火教程参考 | 差异 |
| :--- | ---: | ---: | :--- |
| Generate | **31.65 tok/s** | 23.96 tok/s | **+32% 更快** |
| Prefill | 198.46 tok/s | 305 tok/s | −35% 略慢 |
| 内存 | 977.87 MB | 784 MB | +25% 略高 |

> **为什么 Prefill 慢而 Generate 快**：Prefill 主要受**内存带宽**限制，
> 教程数据可能来自不同内存规格/频率的板子；Generate 是逐 token 解码，
> 更吃 NPU 效率——本机 3 核全开且调度到 A76 大核，故生成更快。
> **对交互式对话而言，Generate 速度才是体感关键**（Prefill 只发生一次且仅 85ms）。

## 4. 延迟预算核算（关键结论）

`docs/05` 的 V8 预算：端到端 **< 3.5 秒**，其中 LLM 占 **600~1200 ms**。

按实测值推算一轮对话的 LLM 耗时：

| 场景 | Prefill | Generate | LLM 小计 | 预算 600~1200ms |
| :--- | ---: | ---: | ---: | :--- |
| 短回复（15 token） | 85.66 ms | 474 ms | **~560 ms** | ✅ 略优于下限 |
| **本轮实测（24 token）** | 85.66 ms | 758 ms | **~844 ms** | ✅ **落在预算内** |
| 长回复（40 token） | 85.66 ms | 1264 ms | **~1350 ms** | ⚠️ 略超上限 |

**结论**：

1. ✅ **LLM 环节完全满足预算**，无需换更小模型，**无需启用任何降级方案**。
2. ⚠️ **回复长度直接决定延迟**。若要保住 1.2 秒上限，
   **应把回复控制在 ~35 token 以内**（约 25~30 个汉字）。
   这与 `docs/03` D5「最多 3 轮」的设计意图一致，建议同时**限制单轮回复长度**。
3. ✅ **V4 假设（首字 1~2 秒）成立**：首字 = Prefill + 1 token Generate
   ≈ 85.66 + 31.60 = **~117 ms**（纯 LLM 部分）。加上 ASR/TTS 后仍有充裕余量。

## 5. 内存结论

| 项 | 值 | 结论 |
| :--- | ---: | :--- |
| rkllm 峰值 | 977.87 MB | |

✅ **内存充足**。RK3588 共 7.7 GiB，模型占约 1 GB，
**剩余 5.6 GiB 足够同时跑 ASR（CPU）+ TTS + WebSocket 服务**。

> 注意：`docs/04` 的存储要求写的是"≥32GB 存储"，那是**磁盘**；
> 这里是**内存**，两者不冲突。模型文件 889.8 MB 需占磁盘。
