## 这一轮做完了什么

用户决定：决定一 **B**（本轮把关联层接进 `VisionService`）、决定二 **D**（`auto` + 可观测）。
两项都落地并在板上验收。

1. **关联层接线**（`vision/service.py`）：每张脸带 `embedding` + `rms_norm`；tracker 回填
   `track_id`；**每帧**喂关联层；出事件时按会话去重；已知人脸不变；v1 协议未改。
2. **决定二 D**：`scripts/check_backend.py`（部署断言）+ 心跳 `backend` 字段 + 启动日志打印
   `实际后端：yunet-onnx/tensorrt`。
3. **板上量出来、必须改的四件事**：质量门 `0.10→0.16`、换轨交接 `tracked_ids`、会话 TTL
   刷新 bug、同帧重复检出先去重。
4. 单测 319 项全过；证据与说明见 [P2.5-关联层接线](../P2.5-关联层接线-2026-11-07.md)。

## P2 要做的（按顺序）

### 0. 先插 USB 摄像头（唯一的硬件前置）

```bash
ssh jetson-nano 'ls -l /dev/video*; v4l2-ctl --list-devices'
```

没有设备就别往下走"实时"那一半，先把真实素材采集补上。

### 1. 实时链路与延迟

```bash
ssh jetson-nano
cd ~/sentinel-quality-20261106
OPENBLAS_CORETYPE=ARMV8 python3 scripts/check_backend.py --profile board   # 必须退出码 0
OPENBLAS_CORETYPE=ARMV8 python3 scripts/vision_sim.py --profile board --no-server --duration 30
```

要记录：fps、单帧推理 ms、丢帧、端到端时延（人脸进画面 → 事件发出，`frame_ts` 与 `ts` 之差）、
心跳里的 `backend` 字段。判据：稳定 ≥15 fps、端到端 <300 ms、无持续丢帧。

### 2. 真机注册再认

```bash
OPENBLAS_CORETYPE=ARMV8 python3 scripts/enroll_faces.py --profile board --camera 0
OPENBLAS_CORETYPE=ARMV8 python3 scripts/vision_sim.py --profile board --no-server --duration 30
```

要记录：同一人 10 次进入的 `is_known` 命中率、`confidence` 分布、错认（把 A 认成 B）次数——错认是硬红线。

### 3. 真实门口素材复评关联层（本轮没素材的那部分）

本轮 `tau=0.45 / margin=0.10 / quality_max_rms=0.16` 是在"公开视频 + 两个人"上验的，剩 1 条
`below_tau`（own 0.38）的保守重报还需真实素材确认是不是可接受：

- 采集：同一人两次进入（间隔 <30 s、>3 s）、不同人先后站同一位置、两人并排、逆光/侧脸。
- 判据：同人不重报（或重报率可接受）、**不同人绝不能合进一条会话**（合错=事故级）。
- 若要调 `tau`：下调前必须先看异类余弦上界（本轮实测 0.330），别把 `tau` 压到 0.40 以下。
- 回放工具可复用：`logs/video-validation/association_replay_board.py`（夹具几何 + 真实外观）、
  `association_service_board.py`（生产几何 + 挖空档）、`measure_assoc_cost.py`（单帧开销）。

### 4. 全量回归 + 联调风险

- `py -3.12 -m vision.run_tests`（本机 319 项）→ 板上 `python3 -m vision.run_tests`（如无 pytest 则用 run_tests 自带的 runner）。
- **已知风险**：WS 连不上时事件发送失败会阻塞主循环（本轮实测同一段视频 8.2 vs 16.5 fps）。
  联调前先起假对话节点，或给 `WsSink` 加重连退避/超时上限。
- 已知人脸的重报仍由业务层 10 分钟窗口负责，本轮没动。

## 未完成 / 遗留风险

**未完成**（都卡在硬件或素材上）：

- 板上无 `/dev/video*`，实时摄像头链路、端到端时延未验（本轮 fps 全部来自视频源）。
- 真实门口素材未采：`tau/margin/质量门` 只在"公开视频 + 两个人"上验过；夹具剩的 1 条事件
  （`below_tau` own 0.38）是合同取舍，还未用真实素材判定可接受程度。
- engine 未部署化：`~/sentinel-quality-20261106/*.engine` 不在仓库，没有"换板自动重建 + 侧车校验"脚本。
- 已知人脸重报仍由业务层 10 分钟窗口负责，本轮未动。

**风险**（按严重度）：

1. 事件发送失败会阻塞主循环（同一段视频 8.2 vs 16.5 fps）——联调前先起假对话节点或给发送加重连退避。
2. `below_tau` 漏关联：真实素材里如果同一个人的姿态变化总是低于 τ，重报率会明显高于本轮水平。
3. `quality_max_rms=0.16` 是在 79 张脸的小样本上定的，换场景（逆光/远距离）需要重测。
