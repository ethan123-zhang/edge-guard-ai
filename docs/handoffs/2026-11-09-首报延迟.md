## 1. 已完成（带证据）

1. **首报延迟**（`vision/service.py`）：会话第一次建出来时**先不发**，同一轨道再撑够
   `first_report_confirm_frames`（3）帧**或** `first_report_confirm_ms`（1000）毫秒，
   先到者为准才真发；撑不住的按残影丢弃，连它建的候选会话一起作废
   （`association.drop_session`）。被判"推翻"的候选会立刻结算：撞上已报过的会话就并回去
   （不是新访客），建不出新会话就丢弃。
2. **两处必须的判据（第一版都写错过，实测抓出来的）**：
   - 计数**按 track_id 各算各的**。第一版"场上有多张脸就不计数"，结果相邻双人（sc02）
     两个人同场 → 后来的人永远撑不满 → 两条 take 的 B 全不报（1/2 通过）。
   - 会话**出生是弱证据**的，后面沿轨 `track_bound` 也算弱口径（要撑 `weak_first_report_confirm_frames`
     = 6 帧）。否则出画残影先 below_tau 建会话、再沿轨 3 帧就骗过确认。判据来自
     `association.created_reason()`（会话上新增 `created_reason` 字段）。
3. **复评结果**（8 条真素材 `datasets/scenarios/real-20261108/`，tau=0.45 / margin=0.10 /
   质量门 0.16）：**关 6/8 → 开 7/8**。修掉的是 `sc02_adjacent_t2`（第十七轮两个残余之一）。
4. **配置**：`vision/config.py` DEFAULTS、`config/base.yaml`、`config/board.yaml` 三处都写了
   3 / 1000 / 6，并注明"关 6/8、开 7/8"的实测依据。`config.validate` 校验负数。
   质量门与弱证据边界例外：`weak_obs` 攒满建出来的候选（below_tau 那一刻）只延后不否决。
5. **评估脚本**：`scripts/scenario_eval.py` 新增 `--defer-frames / --defer-ms`；
   上报记录改以 `service._report` 为准（延迟补发也计入）；`decisions` 行加 `deferred`。
6. **测试**：本机 `py -3.12 -m pytest vision dialog -q` → **476 passed**；
   `py -3.12 -m vision.run_tests` → 401 OK。新增 `TestFirstReportDefer` 7 项 +
   `test_association.TestDropSession` 2 项 + `TestCreatedReason` 语义。
7. **部署**：`pwsh -File scripts\deploy_board.ps1` → 107/107 sha256 一致、
   `check_backend` 走 TensorRT（yunet/sface fp16）、板端 `python -m vision.run_tests` 401 OK(skipped=2)。

## 2. 未完成 / 卡点

  这个人**慢速出画**，残影不是"1–2 帧"而是能连续给 ~10 帧干净正面（余弦 0.286、rms 0.115），

## 4. 风险与注意

- 首报延迟是**全局**行为：所有未知人脸的首报都晚 ~3 帧 / ≤1 s（弱证据 6 帧）。这是有意的取舍
  （残影不算访客），但"一刻不停走过去"的场景可能来不及确认 —— 门宽/帧率改变时要重跑矩阵。
- `_expire_pending` 的超时窗口夹在 1000–2000 ms。调 `first_report_confirm_ms` 超过 2 s 时
  挂起会被提前收走，表现为"设了 3000 却只等 2 s"。
- 板子仍是 `4eef6b9` 之后的本轮代码；engine 绑定 TensorRT 版本，换板/升级 JetPack 先跑
  `python3 scripts/ensure_engines.py --check`。
