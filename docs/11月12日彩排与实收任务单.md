## 4. P1 代码：来意词表补「送菜」

**为什么必须本次改**：正式演示脚本（[05-演示与答辩](05-演示与答辩.md) 0:50）熟人说的是「我来送点菜」，任务书阶段 4（11/13 语音验收）也要求熟人说「来送菜」。按现词表这两句都抽不出来意 → 熟人场景会变成「只留图、无汇总」，与讲稿写的「转告家里人」对不上。

- 改动点：`master/reception.py` 的 `PURPOSE_RULES` 送货组（`:33`）加 `"送菜"`、`"送点菜"`（或「送菜」足够覆盖两句，二者取其一即可；**不要**加单字「菜」，会把「不买菜」之类误判）。
- 单测：`master/tests/test_master_core.py` 的 `ReceptionTest` 补一条——「我来送点菜」→ `purpose == "送货"` 且收口后 `visit_report` 只入队一次。
- 回归：`py -3.12 -m pytest master -q`（当前基线 50 passed）。
- 部署：同步 `master/reception.py` 到鲁班猫 `~/sentinel-master/master/` → `systemctl restart sentinel-master` → 用 `temp/board_reception.py` 同款 API 注入验证「我来送点菜」出汇总。
- 判据：板端注入 → outbox 出现 `kind=visit_report`、`purpose=送货`；手机看板显示来意「送货」。

每例都要留的证据：

1. **看板当前到访卡**：姓名 / 自称 / 来意 / 留言 / 照片 / 越权标记（截图）。
2. **到访编号** `visit_id` 与照片 `msg_id`（两者必须对应，`snapshot_asset.msg_id` 与 `visit_event` 能对上）。
3. **原话**：`dialog_turn.utterance` 与该次到访一致（`master/tests` 语义：消息与到访同号）。
4. **计数**：见 §9 的 SQL，清库后按例累计。
5. **时刻**：录入时刻、告警/汇总入队时刻（`outbox.created_at`）、手机显示时刻。

注意：

- 例 5 是例 3 的否定对照：两句都含「开门」，例 3 必须告警、例 5 必须不告警；只跑一例无法证明规则没误伤。
- 每例只录一句（例 7 的自称与来意在同一句里），收口再单独录一句告别词；多出来的话会进留言，干扰比对。
- 每例之间换人或等窗口（见 §6），否则 10 分钟窗口会把同一人的新到访并到旧记录，计数失真。

## 7. P4 手机锁屏实收（11/12–13）

> 2026-11-12 状态：**未做**。今天只有一人在场，手机锁屏/后台的推送与计时需要人配合；已确认的前提是「APK 无系统通知、锁屏通知只能来自企业微信、企微只发文字」。

前提事实：**APK 无系统通知**，锁屏弹的通知只有企业微信；APK 是查图入口。所以下面三类状态要分别测，才能知道「企业微信到底收不收到」。

### 7.1 三类在线状态

| 状态 | 布置 | 要测的消息 |
|:---|:---|:---|
| S1 无其他看板在线 | 手机关 WiFi 走 4G、APK 退后台 + 锁屏；PC 不开看板 | 越权告警 1 条 + 普通汇总 1 条 |
| S2 另一台看板在线 | 上加：PC 浏览器打开看板（投屏场景） | 同上，重点看企业微信**还收不收到** |
| S3 手机在局域网且解锁 | 手机连 WiFi、APK 前台 | 看板能否直接收到并显示（对照组） |

- 触发方式：**不要在手机上敲字**（锁屏后进不去）。用板端 API 注入：`POST /api/utterance`，body `{"visit_id": ..., "text": ...}`（`master/api.py:120,272-291`），`temp/board_reception.py` 是现成模板（内含 token，已 gitignore）。手机可以一直锁着。
- 注意：到访必须先由**真实人脸事件**产生（人站门口，或按计划末条的 PC 回放），API 只负责「说话」；注入前先确认该 `visit_id` 存在。
- 记录：注入时刻、企业微信消息出现时刻、解锁后 APK 打开看到记录的时刻（三段分开记）。
- 预判（需实测确认）：S2 下 LAN 适配器先成功 → `CompositeAdapter` 直接返回 → 企业微信不发。这正是 §8 决策 D1 的依据。

### 7.2 照片可达性

- 企业微信消息里**没有照片也没有详情入口**（`relay.py` 只发文字）。要按任务书验「点汇总能看这一次的照片」，需要解锁 → 打开 APK → 在当前/历史里找到该到访 → 详情看照片。
- 核对：照片是**这一次**的（不是最近一张），与 `visit_id` 对应。
- 未授权：不带 token、或用错误 token 请求 `/api/visits/<id>/photo` → 必须是 `401`（`master/api.py:233-256`）。

### 7.3 材料里要写的差异

若沿用「企业微信文字提醒，另开 APK 查图」的演法，必须在材料中明示：员工看到的是文字摘要、点开没有图片直链；原指标「点汇总看照片」通过 APK 内查看实现，并说明与原任务书的差异。**不要**在讲稿里写成「企业微信里点一下就能看图」。

## 8. P5 两个需要拍板的决策

### D1 组合推送改不改「两路都投」

- 冲突：现场演示要**投屏看板**（PC 浏览器在线）→ LAN 先成功 → 企业微信不发 → 手机锁屏收不到告警。这与「锁屏推送」的演示目标直接矛盾。
- 选项：
  - **D1-a 改 fan-out**（推荐）：`CompositeAdapter` 两路都投，任一成功即 `sent`，失败只记日志。改动小（`master/push/composite.py:20-30` + 一条单测），但要接受「企业微信失败不重试」。
  - D1-b 不改代码，演示时确保无看板在线：与投屏需求冲突，只能改成「先投屏演完，再关看板演锁屏推送」，脚本变长、现场易忘。
- 风险与边界（写进材料）：企业微信 20 条/分钟限频；fan-out 后同一消息在两处各显一次属预期。

### D2 企业微信文本追加签名照片链接（可选，加分项）

- 现状：照片接口已支持 `?exp=&sig=`（`master/api.py:248-256`、`auth.photo_signature`），只是 relay 没用。
- 做法：relay 的 `report_text` 追加一行「照片：<公网地址>/api/visits/<id>/photo?exp=…&sig=…」，公网地址取板端 `data/public_url.txt`；链接 10 分钟有效。
- 代价：约 1–2 h（含单测与板端验证）；不改协议、不传图、隐私面不变。
- 风险：签名链接**不需要设备 token**，群内拿到链接的人 10 分钟内都能看图（`master/api.py:242-255`）——演示群只有自己人时可接受，材料里要写明。
- 建议：**D1 先做**（演示能不能演的问题），D2 有时间再做（演得更像「手机点开就能看图」）。
