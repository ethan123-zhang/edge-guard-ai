# 业务层 10 分钟到访窗口：从 face_event 到 visit（2026-11-08）

> 合同：[跨轨关联与两层去重合同](跨轨关联与两层去重合同-2026-11-01.md) §业务窗口的建议语义（2026-11-01 用户已确认）
> 协议：[02-接口协议](02-接口协议.md) §3.1 / §4.1 / §6.6
> 证据：[visit-window-2026-11-08.json](data/visit-window-2026-11-08.json)

## 1. 为什么现在做

视觉链路到 2026-11-07 已经通了：摄像头 17.8 fps、检测+识别都在 TensorRT、
关联层把"出画再回"的事件从 5 条压到 3 条、已知人脸再认 conf 0.849。
但**"这条事件算不算一次新的到访"没人算**：

- `dialog/db.py` 的 `create_visit` 直接建行，不实施 10 分钟去重；
- `docs/02` 写着的 `visit_dedup_min: 10` 只是约定，没有代码；
- 2026-11-01 的合同把这条列为"待独立业务合同与实现"。

所以本轮补的是**业务层第 1 层**：`face_event` → 归并到 `visit`，并回答"第 N 次来"。

## 2. 语义（照合同落，不新增数字）

| 规则 | 实现 | 依据 |
| :--- | :--- | :--- |
| 固定窗口 | 以该次到访的 `arrived_at` 起算，`0 <= frame_ts - arrived_at < 600000ms` 并入；**恰好 600000ms 另建** | 合同 §业务窗口（用户 11-01 已确认） |
| 窗口不滑动 | 后续事件只更新 `person.last_seen`，不改窗口起点 | 同上（"窗口不被重复消息滑动延长"） |
| 活跃到访不拆 | `departed_at IS NULL` 且 `completed = 0` 的到访，同人事件一律并入，哪怕超 10 分钟 | 同上（"不能凭计时自动生成新到访"） |
| 陌生人不跨 ID | 每个 `face_id` 各走各的账；`unk_*` 之间不互并 | 同上（"缺少关联时不得跨 unk_ID 套用同人条件"） |
| msg_id 幂等 | 同一条消息重传只处理一次，账本落库（`visit_event`），**重启后仍有效** | 同上（"msg_id 重传只处理一次"） |

`visit_count` 在**到访建立时**累加（不是收口时），因为问候语要当场说"您这是第 N 次来"
（docs/02 §4.1：`visit_count` 含本次，第 1 次来时值为 1）。

## 3. 实现

| 文件 | 内容 |
| :--- | :--- |
| `dialog/visits.py` | `VisitBook.arrive(msg)` → `VisitDecision(visit_id, created, reason, person_visit_count)`；`reason` ∈ `new_visit` / `reuse_active` / `reuse_window` / `replay_msg`；`parse_face_event()` 严格校验（缺字段、类型错、已知人脸没名字都抛 `ValueError`） |
| `dialog/db.py` | 新增 `visit_event` 表（`msg_id` 主键 + `visit_id` + `frame_ts`）与 `latest_visit_for / get_visit_event / log_visit_event / events_for_visit` 四个查询 |
| `scripts/visit_window_replay.py` | 把事件序列回放给 `VisitBook`，断言 11 项规则并落证据 JSON |
| `docs/02-接口协议.md` | §3.1 标注两层去重的归属；§6.6 新增 `visit_event` 表（协议消息本身未变，v1 不加字段） |

代码仍是 Python 3.12/3.6 都能跑的标准库风格；`dialog/` 这一侧按 RK3588 的
Python 版本写，不影响板端（板端只部署 `vision/` 与 `scripts/`）。

## 4. 验收

### 4.1 单测

```
py -3.12 -m dialog.run_tests   → 75 项 OK（本轮 +28：visits 24、回放脚本 4）
py -3.12 -m vision.run_tests   → 353 项 OK（本轮 +1：抑制日志理由）
```

`test_visits.py` 钉住的边界：

- 599999ms 并入 / 600000ms 另建；窗口以 `arrived_at` 为锚，不随事件滑动；
- 活跃到场 20 分钟后再来事件仍是同一次（不被计时拆开）；
- 已收口到访在窗口内并入、窗口外另建、隔天另建；
- 两个已知人各建各的；两个 `unk_*` 不互并；未知事件不覆盖 `person.name`；
- 同 `msg_id` 重传：不建访、不计数、不重复记账；**换进程重连后仍然识别为重传**；
- 新到访 `report_status='pending'`（断网补传链路不受影响）；
- 非法事件（缺 `frame_ts`、类型不对、已知人没名字、非 dict、非正窗口）全部拒绝。

### 4.2 回放证据（`docs/data/visit-window-2026-11-08.json`）

合成已知人脸时间线（窗口 600000ms）：

| 步骤 | frame_ts 偏移 | 结果 |
| :--- | :--- | :--- |
| 到达 | 0 | 新建 `v_20250101_0001`，count=1 |
| 再出现 | +5 min（已收口） | 并入 0001（`reuse_window`） |
| 再出现 | +9 min（已收口） | 并入 0001（`reuse_window`） |
| 再出现 | +10 min＝600000ms | **新建 0002**，count=2 |
| 再出现 | +25 min（0002 仍活跃） | 并入 0002（`reuse_active`） |
| 重传第一条消息 | 0 | 忽略，count 仍 2（`replay_msg`） |

7 项断言全过；`unk_1`/`unk_2` 四条断言全过（两个匿名 ID 各建一次）。

真实夹具 `logs/video-validation/natural-head-full.json`（2026-11-01 自然姿态验收的
12 条 face_event）：**12 条事件 → 12 次到访、复用 0**。

> 这不是业务层的失败，而是**层级边界的证明**：那 12 条事件的 `face_id` 是 12 个不同的
> `unk_*`，合同禁止业务层跨 ID 猜同一个人。要压掉它们得靠视觉层的匿名关联
> （2026-11-07 已接线，同一会话不再重报），业务层只负责"已确认同人"的窗口归并。

## 5. 未完成 / 风险

1. **没有对话节点接线**：仓库里还没有 `dialog/` 的主循环（ASR/TTS/LLM 状态机），
   所以 `VisitBook` 目前只在测试与回放脚本里被调用；真正收消息的那侧还没写。
   接的时候只需：收到 `face_event` → `book.arrive(msg)` → `created` 就开一次迎宾。
2. **离场判定没做**：`face_event` 没有"人走了"的信号，合同明确离场判定另立协议。
   后果：一条从未收口的到访会被永远当成"活跃"，同人隔天再来会并进去。
   当前只在有对话节点调 `finish_visit` 时才会收口 —— 这是已知限制，不是 bug 隐藏。
3. **`visit_report` 构造/推送没做**：`pending_reports` 只是查询，补传循环在对话节点里。
4. **业务窗口不解决自然姿态 12 条**：见 §4.2，那要靠视觉层关联 + 真实素材复评。
5. 真实门口素材到位后要复评的是**视觉层**的 `tau/margin/质量门`，与本节窗口无关。
