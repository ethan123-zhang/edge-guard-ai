# 哨兵管家 — 部署与运维

> 本文档面向**单人开发 + 现场演示**场景，重点是"少装东西、少出故障、出事能快速恢复"。
> 版本：v1.0（主线版）

---

## 1. 环境准备：核心原则

单人项目最大的时间杀手**不是写逻辑，是跟环境搏斗**。因此本项目的环境原则是：

| 原则 | 做法 |
|---|---|
| **能用官方自带的，绝不自己编译** | Jetson 用 JetPack 自带 Python；RK3588 用系统 Python |
| **能不装的依赖，绝不装** | 人脸识别用 OpenCV 自带模型，**不装 insightface 全家桶** |
| **长尾任务提前启动** | 模型下载/转换是"提交后等结果"型，**第一周就挂上** |
| **所有配置外置** | 阈值、地址、开关全在 `config.yaml`，现场可改，不改代码 |

## 2. Jetson Nano B01（视觉节点）

### 2.0 重装系统：烧写官方 JetPack 4.6 SD 卡镜像（**2026-10-20 定案**）

> **为什么重装**：这块 B01 到手时跑的是亚博智能的「出厂镜像_ROS+AI视觉」，环境被改脏 ——
> Python 用的是 Ubuntu 源的 **OpenCV 3.2.0**（无 `cv2.dnn`、无 `cv2.cuda`），55G 卡只剩 6.6G，
> **连编译 OpenCV 的空间都不够**。
> 2026-10-20 已向**官方技术员确认**：这块 **B01 板可以直接用 NVIDIA 官方 JetPack 4.6 SD 卡镜像**，
> 不需要亚博定制镜像。本节即该镜像的取用、校验、烧写与烧后重测。

#### 镜像事实（已实测核对）

| 项 | 值 |
|---|---|
| 文件名 | `jetson-nano-jp46-sd-card-image.zip` |
| 版本 | JetPack **4.6** = L4T **R32.6.1** — Ubuntu 18.04 / **CUDA 10.2** / cuDNN 8.2.1 / TensorRT 8.0.1 / **OpenCV 4.1.1** / Python 3.6.9 |
| 大小 | **6,533,894,369 字节（6.09 GiB）** |
| 官方页面 | <https://developer.nvidia.com/embedded/jetpack-sdk-46> → *Jetson Nano Developer Kits* → *Download the SD Card Image* |
| 直链 | `https://developer.nvidia.com/embedded/l4t/r32_release_v6.1/jeston_nano/jetson-nano-jp46-sd-card-image.zip`（⚠️ 路径里的 `jeston_nano` 是 **NVIDIA 自己的拼写错误**，手打别改） |
| zip 内镜像 | **`sd-blob-b01.img`** —— 文件名里的 `b01` 就是这块载板 |
| 本地路径 | `firmware/jetson-nano-jp46-sd-card-image.zip`（**不入库**，`.gitignore` 已排除 `firmware/`）<br>已解压出裸镜像 `firmware/sd-blob-b01.img`（**13,705,936,896 字节**，SHA256 `544c6af6…22d5d5`） |
| SHA256 | zip：`2ab9f0eaf3ea432419a8fff230659ad1e402f5c03f872097ed620924b1c14ecb`（同目录 `.sha256`）<br>裸镜像：`544c6af63a011bbf2a2e74aaf51a5a55c63c268990b8f2f7a3aebdfebb22d5d5`（解压时 CRC32 已与 zip 内头对过：`478711d1` ✅） |
| 校验记录 | 大小与服务器 `Content-Length` **完全一致**；`zipfile.testzip()` **通过**；zip 内**只有一个文件 `sd-blob-b01.img`（12.76 GiB 未压缩）**。⚠️ NVIDIA **不提供**官方 checksum（`.sha256/.sha1/.md5` 均 404），所以上面这个值是**本机自己记的基线** —— 以后重下要拿它比对 |
| 卡容量 | 未压缩 12.76 GiB → **至少 16G 卡**；本项目用 **32G**（首启 APP 分区选最大后约 28G 可用） |

> **板型口径（2026-10-23 用户确认，纠正 10-22 的误判）**：这块是 **Jetson Nano B01 官方版**（模块 `p3448-0002`），
> **不是亚博 SUB 版**。B01 模块**自带 16GB eMMC**（板端 `mmcblk0`，实测 14.7 GiB）+ 载板 TF 卡槽（`mmcblk1`）——
> **"两个都有"是 B01 的正常形态，不能拿"有 eMMC"倒推成 SUB 版**。
> ⚠️ 因此**别照亚博 SUB 版教程操作**（SUB 是"U 盘镜像 + `flash.sh -r jetson-nano-devkit-emmc` 写 EMMC 引导"），
> 本板走的就是本节这套 **NVIDIA 官方 SD 卡镜像**。亚博出厂镜像的默认账号是 `jetson` / `yahboom`。

**取镜像的工具**：`scripts/download_jetson_jp46.py` —— 走 `127.0.0.1:10090` 代理，
**Range 断点续传**，断了直接重跑同一条命令即续传。
（本机 `curl` / `Invoke-WebRequest` 在沙箱里 TLS 握手直接失败：`schannel: SEC_E_NO_CREDENTIALS`，
所以用 Python 的 OpenSSL 走代理，别浪费时间修 curl。）

> **JP46 还是 JP461？** 4.6.1（R32.7.1）是 4.x 最后一版，同样支持 Nano。
> 本次按官方技术员口径用 **4.6**（教程/博客生态最全）。若日后要 OTA/安全更新再考虑 4.6.1，**别混着用**。

#### ⚠️ 最关键的一条：A02 与 B01 的镜像**不通用**

- JP46 的 zip 解出来是 **`sd-blob-b01.img`**，带的是 B01 的 dtb/pinmux。
- **A02 的 dtb 在 B01 上起不来**：症状是**绿灯亮、HDMI 全黑、连 NVIDIA splash 都不显示**，
  看起来像板子烧了，其实只是镜像不对。
- 反过来 B0x 镜像**可以**在 A02 上跑（官方说明）。所以本项目的规则是：
  **B01 板只认 `sd-blob-b01.img` 这一支**；旧卡（亚博镜像 / 别人的 A02 卡）**不要插到这块板上试**。

#### 烧写（Windows，需要管理员 + 读卡器）

> 两个工具都行，本质一样：**把裸镜像按扇区原样写进卡**（DD/raw 写），和之前烧 RDK 镜像同一个原理。
> 区别只在"**写完会不会读回校验**"：Etcher **默认校验**，Rufus **不校验**。

**方案 A：balenaEtcher（官方推荐，会校验）**

1. （可选）用 [SD Card Formatter](https://www.sdcard.org/downloads/formatter_4/) 快速格式化卡。
2. [balenaEtcher](https://www.balena.io/etcher)：
   - *Select image* → 选 **zip 本身**或 `sd-blob-b01.img` 都行（zip 它自己会解）；
   - *Select drive* → 只选那张 microSD，**别选错盘**；
   - *Flash* → Windows 弹「需要格式化此磁盘吗」→ **取消**；
   - USB3 读卡器约 **10–15 分钟**（含写后校验；**校验必须留着**，校验失败就是卡坏了）。

**方案 B：Rufus（和烧 RDK 一样顺手，但要自己补校验）**

1. 选 **`firmware/sd-blob-b01.img`**（**先解压**，别直接选 zip —— 别赌 Rufus 对压缩包的支持）。
2. 卡在列表里**看不到**时：Rufus「高级选项」→ 勾 **List USB Hard Drives**（不少读卡器被识别成"固定盘"，默认不列）。
3. 选 .img 后一般直接就是 **DD 模式**；若出现 *ISO Image / DD Image* 下拉，**必须选 DD Image**。
   DD 模式下分区类型 / 文件系统 / 簇大小这些下拉**不生效，别去动**。
4. Rufus **不做写后读回校验** → 写入前在「高级选项」勾 **Check device for bad blocks（2 passes）**，
   先确认这张卡不是假货/坏卡（32G 卡要十几分钟，值得）。
5. 写完 Windows 提示格式化 → **取消**。

> 本机没有管理员权限时**不要**试图用 `dd`/`Get-Disk` 自己写盘 —— 交给有 UAC 的终端做。

#### 首次开机（⚠️ **先把串口连好，再上电** —— 2026-10-21 用两个晚上换来的顺序）

> **这块板子的 HDMI 显示通路是坏的**：`tegra-i2c no acknowledge from address 0x54`（读不到显示器 EDID）
> + `dpd enable lookup fail:-19`（显示电源域 ENODEV）。
> `nv-oem-config` 探不到可用显示时**会回退到 micro-USB 串口（ttyGS0）等你输入**，
> 并在第 1 个虚拟终端上打一行：
>
> ```
> A start job is running for End-user configuration after initial OEM installation (20min 10s / no limit)
> ```
>
> **没有超时、不会自己跳过**，按 Alt+F2 也进不去（那台 tty 根本没起）。
> 更坑的是：如果你不知道要去串口，看着 HDMI 上这行字只会以为是镜像坏了。

**正确顺序：**

1. 卡插到 Nano 模块**背面**卡槽；**J48 跳线短接**（选 DC 供电）。
2. **先**用 micro-USB **数据线**把板子连到 PC（设备管理器 → `USB Serial Device (COMx)`），
   打开串口终端，**窗口保持打开**：
   - 工具：`tools\putty.exe`（便携版，已备）
   - **Serial / COMx / 115200 / 8 数据位 / 无校验 / 1 停止位**
   - *Connection → Serial → Flow control = **None***（PuTTY 默认 XON/XOFF，一旦被 Ctrl-S 挂起就黑屏）
   - *Window → Translation → Remote character set = **UTF-8***（否则方框变成 `鈹?`）
3. **再上电**（DC 圆口 5V 4A）。初始化向导会**直接出现在串口窗口里**。
4. 在串口里走完：EULA → 键盘 → 时区 → **用户名/密码/主机名** → **APP partition size 选最大**。
5. 全程**不要断电**（尤其扩分区那一步），走完它自己重启。
6. 重启后回到 `login:`，用刚建的账号登录，立刻跑 §2.0 末尾的三行基线。

> **不要用 `plink -serial` 在 Windows 控制台里跑**：UTF-8 会按 GBK 显示成 `鈹?`，
> ANSI 光标定位会原样打出 `[10;12H` —— 那是终端没渲染，不是板子的问题。换 `putty.exe` 即可。

#### 首次开机失败对照表（**2026-10-21 实测**）

| 现象 | 真因 | 怎么办 |
|---|---|---|
| `A start job is running for End-user configuration … (no limit)`，HDMI 上一直挂着 | 向导在**串口**等输入 | 接 micro-USB，从串口完成向导；**不要断电** |
| HDMI 全黑，但串口有日志 | EDID 读不到（本板已知） | 一切以串口为准，别在显示上纠缠 |
| 向导中途拔电，之后停在 `login:` 但怎么都登不进 | 向导没走完，**用户根本没建成**（`/etc/passwd` 里没这个账号） | 别浪费时间猜账号（`yahboom` 是亚博镜像的账号，官方镜像没有）。**直接重烧重来**，15 分钟比修快 |
| 想把卡插回 PC 离线改账号 | `wsl --mount` **不认 USB 可移动介质**：`HCS/ERROR_INVALID_DRIVE`；`Set-Disk -IsOffline` 直接 `Not Supported` | 离线改卡这条路在 Windows 上基本堵死；能改的只有：① 重烧 ② 板端 U-Boot 单用户（`setenv cbootargs "${cbootargs} init=/bin/bash"`）③ 裸盘读出→WSL loop 挂载→写回（折腾，风险高） |

#### 首启刮不起向导 / 报 debconf 锁——真因与离线修复（**2026-10-22 实测闭环**）

**症状**：串口上只有三行，按 Enter 无反应、板端没有任何可用 shell：

```
debconf: DbDriver "config": /var/cache/debconf/config.dat is locked by another process: Resource temporarily unavailable
System configuration setup wasn't completed. Please reboot device and try again.
```

**真因（已从卡里的 systemd 单元确认）**：

```
/etc/systemd/system/default.target -> nv-oem-config.target
/lib/systemd/system/nv-oem-config-debconf@.service     ← 模板单元
```

JP46 SD 镜像把**默认启动目标**直接设成 `nv-oem-config.target`，而这个 target 会为
\(tty1\) 和 \(ttyGS0\) **各实例化一份** `nv-oem-config-debconf@`：两个向导同时抢
`/var/cache/debconf/config.dat`，先到的那个占着锁在**看不见的 tty1** 上等输入（`no limit`），
后到的立刻报 lock 并退出。所以：**每次开机一字不差地复现，重烧/换镜像全无效** —— 不是随机损坏。

**离线修复：`scripts/jetson-offline-unlock.ps1`**（拔卡→读卡器→usbipd→WSL2→改 ext4→插回）

| 步骤 | 关键点 |
|---|---|
| 直通读卡器 | `usbipd bind --force --busid X`；**usbipd 5.x 的 `-w/--wsl` 直接跟发行版名**（`attach --wsl Ubuntu-22.04 -b X`），**没有 `--distribution` 这个选项** |
| 定位目标盘 | 扫描 `TRAN=usb` 且 GPT 里有 `PARTLABEL=APP` 的盘（本板 SD 是 **`mmcblk1`**；`mmcblk0` 是 14.7G 机载 eMMC） |
| 建账号 | x86 WSL 跑不了 ARM64 的 `useradd` → 直接改 `etc/{passwd,shadow,group}`；哈希用 `openssl passwd -6`（退化：python `crypt` / `perl crypt`） |
| 关掉向导 | 把 `/lib/systemd/system/*oem-config*` 全部 `ln -sf /dev/null <卡>/etc/systemd/system/`，并把 `default.target` 指回 `multi-user.target` |
| 放开串口 | `getty.target.wants/serial-getty@ttyGS0.service -> /lib/systemd/system/serial-getty@.service`（不做这步：没有显示器的板子起机后没人能登录） |
| 顺手 | 时区/主机名、启用 `ssh`、`default.target=multi-user`（无显示，省内存） |

**扩分区（12.7G → 29.7G）——踩过的一个坑**：`parted --script resizepart` 对**挂载中**的分区照样
交互问 `Yes`，`--script` 不顶用，必须喂输入：

```bash
printf 'Yes\n62333918s\n' | sudo parted ---pretend-input-tty /dev/mmcblk1 resizepart 1
sudo resize2fs /dev/mmcblk1p1        # ext4 在线扩容，无需重启
df -h /                              # 30G，可用 ≈17G
```

**顺手按住的噪音**：`docker.service` 会因内核缺 `dm thin-pool` 无限重启、刷满 tty1：

```bash
sudo systemctl mask docker.service docker.socket containerd.service
```

#### 内核/模块版本错配（2026-10-22 发现，**2026-10-23 已解决并定版**）

**先记住结论**：`uname -r` 与 `ls /lib/modules` 必须**完全相同**（还有 `vermagic` 校验，差一个小版本也拒绝加载）。
内建驱动正常，所以错配时系统"能开机、看着没问题"，但 `wlan0`（RTL8822CE 是模块）、
`nvzramconfig`/`nvpmodel`/`systemd-modules-load` 全部静默失效。

**eMMC 到底是什么版本（2026-10-23 实测）**

eMMC 的 APP 分区是个**空壳**：只有 `boot/ media/ root/ var/ + README.txt`，
`README.txt` 写着 `Download and extract the sample filesystem to this directory.`
—— 这是 `Linux_for_Tegra/rootfs/` 解压 sample rootfs 之前的占位目录，
也就是 **eMMC 只刷了 BSP（cboot + 内核 + dtb），从来没装过系统**。
所以里面**没有** `/etc/nv_tegra_release`、没有 `/etc/os-release`、没有 `/lib/modules`。

版本只能从内核镜像里读：

```bash
sudo mount -o ro /dev/mmcblk0p1 /mnt/emmc
strings /mnt/emmc/boot/Image | grep -m1 'Linux version'
# Linux version 4.9.299-tegra (buildbrain@mobile-u64-5333-d8000) … #1 SMP PREEMPT Tue Nov 22 09:24:39 PST 2022
```

→ **L4T 32.7.3 / JetPack 4.6.3**。

**官方没有配套的 SD 卡镜像**（别再找了）

| 版本 | 内核 | 官方 Nano SD 卡镜像 |
|---|---|---|
| 4.6 / R32.6.1 | 4.9.253 | ✅ 有（本项目手上这张） |
| 4.6.1 / R32.7.1 | 4.9.253 | ✅ 有 |
| 4.6.2 / 4.6.3（32.7.2 / 32.7.3） | 4.9.253 / **4.9.299** | ❌ 只有 BSP + sample rootfs |

**解法 A（推荐，零风险）：只给根分区补模块树，不动 eMMC 引导链**

```bash
# PC 侧：下 BSP（t210 列！不是 t186）
#   Jetson-210_Linux_R32.7.3_aarch64.tbz2  (~267 MB)
# 取内核包 → 抽 lib/modules
python scripts/extract_deb.py \
  Linux_for_Tegra/kernel/nvidia-l4t-kernel_4.9.299-tegra-32.7.3-*.deb \
  out ./lib/modules/4.9.299-tegra
#   （R32.7.x 的载荷是 data.tar.zst，脚本会交给 bsdtar）
# 另取 nvidia-l4t-firmware 里的 lib/firmware/rtl8822_setting.bin（rtl8822ce.ko 只依赖这一个）
# 打成一个包：lib/modules/4.9.299-tegra/ + lib/firmware/rtl8822_setting.bin  → 约 20 MB

# 板侧
sudo tar -xzf jetson-4.9.299-modules.tar.gz -C /
sudo chown -R root:root /lib/modules/4.9.299-tegra
ls /lib/modules          # 应出现 4.9.299-tegra
sudo modprobe rtl8822ce  # 无报错即成功
ip -br link | grep wlan  # wlan0 出现
```

**不要做的事：把 eMMC 的内核降级成 4.9.253。**

试过，走不通：换 4.9.253 的 `Image` + `initrd` + 官方 b00 dtb 之后，
`dmesg` 里**只剩 `sdhci-tegra.3`（eMMC）**，SD 控制器 `sdhci-tegra.0/.1` 一个都不注册，
`mmcblk1` 不存在 → 掉进 initramfs 的 `bash-4.4#`。

⚠️ **真正的开关是 dtb，不是内核版本**：`boot/extlinux/extlinux.conf` 的
`FDT /boot/kernel_tegra210-p3448-0002-p3449-0000-b00-user-custom.dtb`（**237290 字节，2024-12-20**）
才是这块板认 SD 卡的那份；换成官方 b00（237113）就**没有 SD 控制器**。
判据：正常启动的 `dmesg | grep sdhci-tegra` 应同时有 `.3`（eMMC）和 `.0/.1`（SD）。

**eMMC 上必须保留的备份**（都已在 `/boot`）：`Image.4299`、`initrd.4299`、
`custom.bak`（= 那份 237290 的 dtb）、`extlinux.bak`。

**解法 B：换亚博出厂镜像**（有现成 ROS/YOLO/CUDA 环境）
`出厂镜像_ROS+AI视觉/TF卡使用镜像/` 下 `JetsonNano_ros_yolo26.zip`（29.3G）或
`jetson_nano_b01_TF_20250324.zip`（29.9G），**JetPack 4.6.3 → 模块 4.9.299，与 eMMC 天然配套**。
但解压出的 `.img` 是 **58 GB**，64GB 卡（实际 ≈59.6 GiB）临界，**建议 128GB**；
账号是 `jetson` / `yahboom`；OpenCV 仍是 4.1.1（无 YuNet）。

### 2.1 硬件准备

|---|---|---|
| 供电 | **5V 4A DC 圆口**（推荐）或高质量 5V2.5A MicroUSB | 供电不足会随机重启，是 Nano 最常见的"玄学故障" |

#### ⚠️ 千万不要用 `pip3 install opencv-python` 补

原文档此处曾建议 `pip3 install opencv-python==4.8.1.78`，**这条已废弃**，原因有三：

1. **会丢掉 GPU 加速**：JetPack 自带的 OpenCV 是 **NVIDIA 用 CUDA 编译**的，能用上 Nano 的
   128 核 Maxwell GPU；而 PyPI 的 `opencv-python` 是**纯 CPU 轮子**。装上就把
   `docs/01` §3.1"选 Jetson 就是因为有 GPU"这个前提给废了。
2. **该版本在 Python 3.6 上装不了**：`opencv-python 4.8.1.78` **没有 cp36 轮子**
   （OpenCV 4.8 最低 Python 3.7），照抄必然失败。
3. **半覆盖最难排查**：pip 版进 `~/.local/lib/python3.6/site-packages`，
   apt 版在 `/usr/lib/python3/dist-packages`，`import cv2` 会优先拿到 pip 版，
   系统那套**实际被屏蔽但仍在**，出问题时很难判断用的是哪一个。

**正确做法**：装社区预编译的 **CUDA 版 OpenCV 4.5+** wheel（Jetson 生态常见来源），
并**装到独立路径（venv 或独立前缀）**，不覆盖系统 OpenCV，
这样"自带那套"始终可退回。装法与校验见下节。

### 2.6 开机自启（必做）

现场如果设备重启，**必须自动恢复服务**，不能靠人工 SSH 上去敲命令。

`/etc/systemd/system/sentinel-vision.service`：

```ini
[Unit]
Description=Sentinel Vision Service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=nvidia
WorkingDirectory=/home/nvidia/sentinel/vision
ExecStart=/usr/bin/python3 /home/nvidia/sentinel/vision/face_service.py
Restart=always
RestartSec=5
StandardOutput=append:/var/log/sentinel-vision.log
StandardError=append:/var/log/sentinel-vision.log

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable sentinel-vision
sudo systemctl start sentinel-vision
sudo systemctl status sentinel-vision
```

> `Restart=always` + `RestartSec=5` 是**断线自愈**的关键：程序崩溃或被网络断开导致退出，5 秒后自动重来。

#### 步骤 ①：准备 x86 Linux 环境

**RKLLM-Toolkit 只有 Linux 的 wheel，Windows 装不了。** 用 **WSL2**（推荐，最省事）：

**① -0 先配代理（否则 WSL 里下载极慢或直连失败）**

```bash

# 设成变量后配置（把 IP 换成上一步查到的）
PROXY="http://172.28.240.1:10090"

# git
git config --global http.proxy  "$PROXY"
git config --global https.proxy "$PROXY"

# pip
mkdir -p ~/.pip
printf '[global]\nproxy = %s\nindex-url = https://pypi.tuna.tsinghua.edu.cn/simple\ntrusted-host = pypi.tuna.tsinghua.edu.cn\n' "$PROXY" > ~/.pip/pip.conf

# 验证
curl -s -o /dev/null -w "HTTP=%{http_code}\n" -x "$PROXY" https://github.com
```

> 本仓库已提供一键脚本：`scripts/wsl_setup_proxy.sh`（把 `PROXY_HOST` 改成实际网关即可）。

**① -1 装 Toolkit**

### 3.4 麦克风（**唯一必须新购的硬件**）

**问题**：原有麦克风噪声太大。教室是混响环境（大空间、硬墙面），单麦基本不可用。

**远场拾音（1~3 米）的三个必要条件**：

| 需求 | 为什么 | 怎么判断 |
|---|---|---|
| **麦克风阵列 + 波束成形** | 单麦在混响中不可用 | 至少 2 麦，4 麦更好 |
| **硬件 AEC（回声消除）** | 播报时喇叭声音会被录进去 | 产品页写"回声消除" |
| **降噪 / VAD** | 判断客人说完了没有 | 通常与 AEC 一起提供 |

**选型建议（按优先级）**：

1. **ReSpeaker USB Mic Array（4 麦阵列）** — **首选**。Linux 免驱，当 USB 声卡用，资料多，自带 AEC/降噪/波束成形。
2. **带降噪的 USB 会议全向麦** — 便宜保底方案，AEC 靠软件补。
3. **ReSpeaker 2-Mic Pi HAT** — 便宜，但是 **I2S 接口，鲁班猫 40pin 未必兼容**，需先查引脚定义。**有风险，不推荐赶时间时选。**

**买前验证清单**：
- [ ] USB 免驱（Linux `arecord -l` 能识别）
- [ ] 明确标注支持 **AEC / 回声消除**
- [ ] 拾音距离 ≥ 3 米
- [ ] 有 Linux 下的使用案例

**到货后验证**：

```bash
arecord -l                          # 应能看到设备
arecord -d 5 -f cd test.wav         # 录 5 秒
aplay test.wav                      # 回放确认
```

### 3.5 麦克风门控（**最重要的保命机制**）

**问题**：TTS 播报时，喇叭的声音会被麦克风录进去 → ASR 转出系统自己的话 → LLM 又回应 → **自问自答死循环**。教室混响会让这个问题更严重。

**解决方案（按可靠性排序）**：

| 方案 | 做法 | 可靠性 |
|---|---|---|
| **软件门控（推荐）** | 播报期间不读麦克风数据；播报结束后延时 300ms 再开 | 高，成本为零 |
| 静音麦克风 | `amixer set Capture nocap` / 恢复 `cap` | 高，但依赖声卡支持 |
| 硬件 AEC | 依赖麦克风阵列能力 | 中，看硬件 |

**必须实现软件门控**：

```python
def speaking(text):
    mute_mic()                       # ① 关麦
    tts_play(text)                   # ② 播报
    time.sleep(POST_TTS_DELAY)       # ③ 等混响消散（300ms）
    flush_audio_buffer()             # ④ 丢弃缓冲里的残留音频（关键！）
    unmute_mic()                     # ⑤ 开麦
```

> **第 ④ 步是最容易漏的**：即使关了麦，**音频缓冲里可能还留着播报期间采集的数据**，不丢弃的话开麦后立刻被当成"用户说话"。**必须清空缓冲区。**

**验证方法**：让系统连着播报两次，看它会不会自己接自己的话。**没有自问自答才算通过。**

### 3.6 ASR / TTS 部署

**ASR（本地离线，CPU 运行）**：

```bash
pip3 install sherpa-onnx
# 下载中文模型（SenseVoice 或 Paraformer）
```

**为什么 ASR 用 CPU 不用 NPU**：RK3588 的 NPU 资源**被 LLM 占用**。若 ASR 也抢 NPU，会互相阻塞，导致两边都变慢。ASR 放 CPU 上跑，与 LLM 并行，整体延迟更低。

**TTS（本地离线）**：

```bash
# 方案一：piper（轻量、快）
# 方案二：edge-tts（需要外网，不推荐现场用）
# 方案三：预生成音频文件 + aplay（最稳，见下）
```

> **强烈建议的优化**：**把固定话术预先生成为音频文件**（问候语、拒绝话术、收尾语），直接 `aplay` 播放。
> 好处：① 省掉 TTS 合成时间，体感明显变快；② 不受网络/模型影响，演示极稳；③ 只有 LLM 的自由回复才需要实时合成。
> **这是性价比最高的优化手段。**

## 4. 网络方案（现场是手机热点）

### 4.1 关键认知：热点后面是 NAT

```
门口设备(192.168.43.x) → 手机热点 → 运营商 NAT → 互联网
                                              ✗ 外部连不进来
```

**因此**：
- ❌ 不要让主人端在"外网"连设备（连不上）
- ❌ 不要依赖云端 MQTT（教室热点未必有外网）
- ✅ **主人端连同一个热点，局域网直连** —— 这是本版本的方案

### 4.4 断网降级

本版本无外网依赖（ASR/LLM/TTS 全本地），因此：

| 情况 | 影响 | 处理 |
|---|---|---|
| 手机热点断开 | 主人端收不到推送 | 数据写库（`pending`），热点恢复后自动补传 |
| 两台板子之间断连 | 视觉事件发不出去 | Jetson 侧本地缓存事件，重连后补发 |
| 完全没有网络 | 只能本机演示 | **准备"纯本机模式"**：在鲁班猫上直接跑对话，用本地回环 |

**断网补传的验证方法**（这是答辩亮点，必须能演示）：

1. 关掉主人端
2. 完整走一遍迎宾流程
3. 检查数据库：`sqlite3 data/sentinel.db "SELECT visit_id, report_status FROM visit;"`
   → 应为 `pending`
4. 打开主人端
5. 检查：记录自动变成 `sent`，且主人端收到了这条推送

## 5. 现场配置清单（可调参数）

**所有阈值必须在配置文件里，不要写死在代码里。**现场环境一变，改配置比改代码快一百倍。

| 参数 | 文件 | 现场调整场景 |
|---|---|---|
| `detection.score_threshold` | vision | 漏检多 → 调低；误检多 → 调高 |
| `recognition.match_threshold` | vision | 熟人认不出 → 调低；认错人 → 调高 |
| `roi.*` | vision | 观众误触发 → 缩小 ROI |
| `min_face_px` | vision | 远处人误触发 → 调大 |
| `camera.exposure_value` | vision | 画面太亮/太暗 |
| `dialog.max_rounds` | dialog | 演示时间紧 → 调到 2 |
| `asr.vad_silence_ms` | dialog | 判停太慢 → 调到 500 |
| `mic.post_tts_delay_ms` | dialog | 自问自答 → 加大到 500 |

**建议做一个"演示档"配置**：把参数调成"演示友好"（识别宽松、对话短、延迟低），现场一键切换。

## 6. 故障排查手册（**打印一份带到现场**）

### 6.1 视觉节点

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 摄像头打不开 | 设备号变了 / 被占用 | `ls /dev/video*`；`fuser /dev/video0` |
| 检测不到人脸 | 阈值太高 / 光照差 / ROI 错 | 打印检测分数；临时 `roi.enabled=false` |
| 熟人认不出 | 阈值太高 / 光照变了 | 临时降 `match_threshold` 到 0.3 |
| 帧率极低 | 散热降频 / 分辨率太高 | 检查温度；降到 640×480 |
| 随机重启 | **供电不足** | 换 5V4A 电源和短线 |
| 连不上对话节点 | IP 变了 / 服务没起 | `ping`；`systemctl status sentinel-dialog` |

### 6.2 对话节点

| 现象 | 可能原因 | 排查 |
|---|---|---|
| LLM 加载失败 | 模型文件损坏/路径错 | 检查路径与文件大小 |
| NPU 报错 | 驱动版本不匹配 | `sudo cat /sys/kernel/debug/rknpu/version` |
| **系统自问自答** | **闭麦失效** | 检查 `mute_during_tts`；加大 `post_tts_delay_ms`；确认清空了缓冲区 |
| **听不到说话** | 麦克风选错设备 | `arecord -l`；在配置里指定设备号 |
| 对方听不到播报 | 音量/输出设备错 | `aplay -l`；`alsamixer` 调音量 |
| 说话后没反应 | VAD 没判停 | 看日志是否有 `LISTENING → THINKING` |
| 回复很慢 | 上下文太长 | 缩短提示词；`max_new_tokens` 降 64 |
| 回复乱码/带符号 | LLM 输出格式问题 | 检查后处理是否生效 |

### 6.3 网络

| 现象 | 排查 |
|---|---|
| 主人端打不开 | 确认手机连的是同一个热点；`ping 192.168.43.10` |
| 推送收不到 | 看日志推送是否报错；查 `report_status` |
| 热点频繁断 | **换有线**；或换一个热点；把设备放近 |
