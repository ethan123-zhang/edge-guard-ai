# 解码先验预计算（2026-11-07，P0）

## 目的与边界

把旧解码器每帧在纯 Python 里重建 5875 个先验框的 **≈31 ms** 从检测热路径里拿掉，
落成生产模块 `vision/yunet_decode.py`。硬约束只有一条：**与旧实现逐帧等价**——
检出脸数、bbox、5 点、score 全部相同（IEEE float32 位级），因为板端回归和后续
P1 都拿旧 `decode()` 当参照物。

边界：本轮只做「解码」这一件事，**没有接 `VisionService`**，生产默认路径仍是
CPU dnn / Haar，`trt` 仍未启用；SFace、对齐、事件链、关联层都没动。

## 设计

1. **先验表模块加载时算一次**：四档网格（40/20/10/5 步长 8/16/32/64）生成
   `(5875, 4)` 的 float32 缓存 `_PRIORS`；热路径只做「按分数筛 → 解偏移 → NMS」。
2. **顺序绑定不可动**：先验表顺序必须是旧实现的 `y 外 / x 中 / m 内`——ONNX 输出
   行号与先验序号绑定，换顺序**不报错但会把所有框解错**，所以有单测逐行比对顺序。
3. **公式顺序照抄**：`center = prior.xy + loc.xy * 0.1 * prior.wh`、
   `wh = prior.wh * exp(loc.wh * [0.1, 0.2])`、`points` 用同一套 0.1 缩放，逐字节一致；
   没有「顺手向量化」重写表达式。
4. **NMS 语义不变**：仍用 `cv2.dnn.NMSBoxes(score_thr=0.9, nms_thr=0.3, top_k=5000)`，
   返回仍是 15 列 float32 行。
5. **板端可跑**：Python 3.6 语法（无 dataclasses / 海象 / `from __future__`），
   由 `vision/tests/test_py36_compat.py` 自动纳入闸门。

## 验收（固定视频 40 帧，`index % 43 == 0`，同一哈希视频与模型）

| 指标 | PC（cv2 4.13 / numpy 2.4） | 板端（cv2 4.1.1 / numpy 1.19.5） |
| --- | --- | --- |
| 检出脸数 | 旧 69 / 新 69 | 旧 69 / 新 69 |
| 数量不一致帧 | 0 / 40 | 0 / 40 |
| **逐位完全相同帧** | **40 / 40** | **40 / 40** |
| bbox 最大绝对差 | 0.0 px | 0.0 px |
| 解码中位耗时 | 5.796 ms → **0.217 ms（27×）** | 32.689 ms → **0.799 ms（41×）** |
| 解码最大耗时 | 11.194 ms → 0.341 ms | 49.857 ms → 0.949 ms |

板端目标 **<5 ms**，实测中位 0.799 ms，有 6 倍余量。本机全量单测 **239 项通过**
（原 228 + 新增 11，`py -3.12 -m vision.run_tests`，1.26 s）。

## 检测段端到端（板端，复用现有 `yunet_fp16.engine`，5 次预热后 40 帧中位）

| 组成 | 耗时 |
| --- | --- |
| TensorRT `run()`（H2D + execute + D2H + sync） | 21.50 ms |
| 新解码（跑在 engine 输出上） | **0.91 ms** |
| 旧解码（同一份 engine 输出） | 31.49 ms |
| **TRT 检测段 = run + 新解码** | **22.53 ms** |
| CPU 检测段 = dnn forward + 新解码 | 49.15 ms |

对比 11-06 记录的同口径「TRT 检测段（run + 旧解码）」**45.87 ms → 22.53 ms，2.0×**；
CPU 路径 83.8 → 49.15 ms。至此检测段已经接近 engine 自身的成本，TRT 的收益不再被
解码吃掉一半。

⚠️ **口径提醒**：昨天文档里写的「engine 11.7 ms」是另一次测量（不含输出回传），
今天同一脚本里 `run()` 含 H2D/D2H 是 21.5 ms（min 21.37，40 帧很稳）。这不是回退，
是两种测法；以后比较 TRT 收益请在同一脚本内比，别跨文档对数字。
