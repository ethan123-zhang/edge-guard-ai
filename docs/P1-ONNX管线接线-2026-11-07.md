# P1：裸 ONNX 管线接进 VisionService（2026-11-07）

## 一句话

板上默认路径从「Haar（无关键点 → 只能报陌生人）」换成 **YuNet + 五点对齐 + SFace 的裸 ONNX 管线**
（`runtime.backend: auto`）：整链 **3.69 fps → 17.65 fps（4.8×）**，特征与旧路径**余弦 1.000000**、
逐帧检出与 bbox 完全一致、事件条数不变。顺带在板上抓到一个**只在 OpenCV 4.1.1 出现的批量 dnn 缺陷**，
已钳成「CPU 一次只喂 1 张」并用单测钉死。

## 为什么必须自己写这条管线

板上 OpenCV 是 4.1.1：`cv2.FaceDetectorYN` 和 `cv2.FaceRecognizerSF` 都没有。所以板上生产一直是
Haar + 「识别不出特征」——Haar 框没有 5 个关键点，SFace 无法对齐，只能 `NullRecognizer` 式地报陌生人。
P0 把解码算快了，P1 把「检测 → 对齐 → 特征」这三段用 `cv2.dnn` / TensorRT 重新拼起来，
这样**不需要升级 OpenCV** 就能在板上认出人。

## 改了什么

| 文件 | 内容 |
| :--- | :--- |
| `vision/align.py`（新，S1） | 五点相似变换对齐：Umeyama SVD 求 2×3 矩阵，`crop()` 出 112×112。与原生 `cv2.alignCrop` 比过（把模型拷到 ASCII 临时目录），残差一致 |
| `vision/yunet_decode.py`（P0） | `decode(outputs, score_threshold=...)`：阈值跟 `detection.score_threshold` 走，不再固定 0.9 |
| `vision/onnx_pipeline.py`（新，S2） | `DnnRunner` / `TrtRunner`；`OnnxYunetDetector`（320 blob → 解码 → 按 `w/320`、`h/320` 缩放回原图，`raw_row` 原样留给对齐）；`OnnxSfaceRecognizer.embed_batch`（分块、L2 归一化、对不齐返回 `None` 且位置不变）；`create_pipeline`（引擎选择 + 逐组件回退 + 预热）；`create_components`（`legacy/auto/cpu/trt` 统一入口） |
| `vision/service.py`（S3） | 一帧一次批量识别：`_embeddings()` 先收齐这一帧的脸再提特征，`_match()` 独立出来；批量返回条数不符时**退回逐张**（硬凑会把特征和脸对错位） |
| `vision/config.py` + `config/base.yaml` | 新键 `runtime.backend / detector_onnx / detector_engine / recognizer_engine / recognizer_batch / warmup`，`validate()` 逐条点名报错 |
| `vision/config/board.yaml` | 板档切 `backend: auto` + 板上绝对路径（engine、320 声明版 YuNet、动态 batch SFace） |
| `scripts/vision_sim.py` | 走 `create_components`；新增 `--backend` 覆盖；启动失败也接住 `PipelineUnavailable` |
| `scripts/enroll_faces.py` | 同上；检测器检查接受 `yunet-onnx`（否则板上永远没法注册人脸） |
| 单测 | **283 项全过**（原 252 + 31）：`test_align.py` 11、`test_onnx_pipeline.py` 15、`test_config.py` +9（含板档）、`test_service.py` +4（批量）/`test_yunet_decode.py` +2 阈值 |

### 5. 回退与失败

| 场景 | 期望 | 实测 |
| :--- | :--- | :--- |
| `auto` + engine 不存在 | 回退 CPU 且日志说清楚 | `[vision] 检测走 CPU dnn：yunet_trt320.onnx` / `识别走 CPU dnn` / `批量从 8 钳到 1` |
| `trt` + engine 不存在 | 直接报错，不静默降级 | `PipelineUnavailable: 检测配置要求 trt，但…missing.engine` |
| PC 上 `--backend auto` | ONNX 读不了就退旧路径 | `[vision] 警告：ONNX 管线不可用，回退旧路径：…Can't read ONNX file` |

### 6. 计时口径对齐（重要）

P0 记的 `trt_run_only = 21.50 ms` 与本轮 `TrtRunner.run` 的 14.98–16.38 ms 是**同一个 engine、同一个 blob**
（`engine_timing_board.py` 复现 P0 的调用方式确认）。差别来自 P0 的循环把 CPU 前向和 engine 交替跑：
H2D/D2H 是 CPU 侧 memcpy，被 4 线程 dnn 抢总线时会拖慢，于是 engine 看起来慢了一倍。
**规划用本轮的「整段」数字**（检测段 52.6 ms CPU / 15.0 ms TRT，识别段 218.8 / 36.8），
单独比 engine 时请注明是否与 CPU 前向混跑。

## 关键发现：OpenCV 4.1.1 的批量 dnn 会把整批特征塌成同一个

现象（`logs/video-validation/debug_sface_batch_board.py`，板上）：

```
batch 1 | cos [1.0]                       # 对
batch 2 | cos [-0.06843, -0.06843]        # 两张脸变成同一个向量
batch 8 | cos [-0.045497] × 8             # 八张脸全是同一个
round 2 batch 1 | cos [-0.045497]         # 状态被粘住，连单张都回不去了
```

同一模型在 PC（OpenCV 4.13）上批量完全正常（batch 3 每行余弦 1.000000）。**命名输出不是原因**
（`forward()` 与 `forward(['fc1'])` 在板上余弦也是 1.0），是 4.1.1 的批量前向本身。
一旦触发，net 内部状态会被污染，之后单张前向也算了错的特征 —— 这正好解释了第一次板端验收里
69 张脸余弦中位数 0.236 的离群结果。

处置：
- `DnnRunner.max_batch = 1`（`TrtRunner.max_batch = 8`），`OnnxSfaceRecognizer` 用
  `min(配置, runner.max_batch)` 逐级下钳；
- 被钳时**必打日志**（`识别批量从 8 钳到 1：…`），不静默；
- 单测 `test_one_face_at_a_time_when_runner_cannot_batch` / `test_batch_clamp_is_logged_when_dnn_cannot_batch` 钉死。

副作用：CPU 路径本来也几乎吃不到批量收益（每脸 ~109 ms，串行），TRT 的批量收益保留（整段 218.8 → 36.8 ms）。

## 边界与风险

- **关联层仍未接线**，「自然姿态 12 条事件」问题没动；本轮只保证「换后端不改行为」。
- 板上仍**没有 `/dev/video*`**（只有蓝牙），实时延迟/端到端触发时延没测，P2 要插 USB 摄像头。
- `board.yaml` 现在默认 `auto`：**没 engine 时会退到 3.7 fps 的 CPU 路径**（日志会说明），
  想强制失败请设 `trt`。engine 与 TensorRT 版本/设备绑定，换板或升级 JetPack 必须用
  `logs/video-validation/trt_regression.py` 重建（sidecar 会拦版本漂移）。
- PC 上跑不了 CPU/TRT 路径：仓库在 `E:\哨兵管家`，`cv2.dnn.readNetFromONNX` 读不了中文路径
  （P0 同一个坑，需把模型拷到 ASCII 目录）。PC 只用 `legacy`。
- 未做：摄像头实时、低光/多脸性能、`enroll_faces` 在板上的真机采集（脚本已接好但没插摄像头）。
