# 2026-10-23（下半天）— eMMC 版本实测定版 + 内核/模块错配收尾

> 上午的结论见 `2026-10-23-板型纠正与镜像选择.md`（那里还写着"eMMC 版本查不出来"）。
> **本文件推翻那条**：eMMC 版本这次用串口直接读出来了。

## 1. 这一轮要回答什么

用户问：「先检查开发版上 eMMC 镜像的具体版本，再告诉我装什么版本的 SD 卡镜像。」
—— 这正是 E-35「内核/模块错配」的根，上午只是猜，这次要实测。

## 2. 实测结论：eMMC = L4T 32.7.3 / JetPack 4.6.3

板子当时**能启动**（跑的是 eMMC 的 4.9.299 内核 + TF 卡的 32.6.1 根分区），
所以走 micro-USB 的 **ttyGS0 串口（COM16）** 进去，`sudo mount -o ro /dev/mmcblk0p1 /mnt/emmc` 直接读。

| 项 | 实测值 | 依据 |
|---|---|---|
| eMMC 根分区 | 14G 分区上只有 **687M** 的 ext4，内容是 `boot/ media/ root/ var/ README.txt` | `README.txt` 内容：`Download and extract the sample filesystem to this directory.` → **这是 `Linux_for_Tegra/rootfs/` 解压 sample rootfs 之前的占位目录**，即 eMMC 只刷了 BSP，从来没装过系统 |
| eMMC 内核 | **`4.9.299-tegra`**，`buildbrain@mobile-u64-5333-d8000`，GCC 7.3.1 Linaro，`#1 SMP PREEMPT Tue Nov 22 09:24:39 PST 2022` | `strings /mnt/emmc/boot/Image \| grep 'Linux version'` |
| 对应 L4T | **32.7.3（JetPack 4.6.3）** | 4.9.299 + 2022-11-22 编译，与 R32.7.3 发布页／社区实测一致 |
| 引导配置 | `FDT /boot/kernel_tegra210-p3448-0002-p3449-0000-b00-user-custom.dtb`（**237290**），`APPEND ${cbootargs} … root=/dev/mmcblk1p1` | `cat /mnt/emmc/boot/extlinux/extlinux.conf` |
| TF 卡（当时根分区） | L4T **R32.6.1**（GCID 27863751，2021-07-26），Ubuntu 18.04.5，模块只有 `4.9.253-tegra` | `cat /etc/nv_tegra_release` / `ls /lib/modules` |

**关键认知：eMMC 里没有 `/etc/nv_tegra_release`、没有 `/etc/os-release`、没有 `/lib/modules`。**
所以"查 eMMC 版本"只能靠 `boot/Image` 里的 `Linux version` 字符串（含 buildbrain 主机名 + 编译日期 + 工具链），
不能指望 rootfs 里的版本文件 —— 元数据在这台板上根本不存在。

→ 「去官网下个和 eMMC 配套的 SD 镜像」这条路**不存在**。要么用亚博出厂镜像，要么自己补模块。

## 4. 走了两条错路，真因都不是"版本"

**错路一：把 eMMC 内核降级成 4.9.253（配手上的 JP46 卡）。**
换了 `Image` + `initrd` + `kernel_...-b00.dtb`（237113）之后开不了机，掉进 initramfs 的 `bash-4.4#`。
`dmesg` 里只有 `sdhci-tegra.3`（eMMC），**SD 控制器 `sdhci-tegra.0/.1` 一个都没注册** → `mmcblk1` 从头到尾不存在。

**错路二：以为换回原 dtb 就行 —— 但那次 `cp` 没生效。**
一个长命令里夹着 `cp`，敲错/漏字后 `sync; reboot -f` 照样执行，于是仍然用 237113 的 dtb 启动。
最后靠 `ls -l /m/boot` 才看出来：`-user-custom.dtb` 一直是 **237113 / 2021-07-21**（4.9.253 那套），
而真正的原配 **237290 / 2024-12-20** 一直躺在 `custom.bak` 里没被用上。

**换回 237290 之后：`mmcblk1` 立刻出现**（虽然紧接着就是 CRC 报错，那是另一件事）。

> 教训：**这块板上，内核对不够只是必要条件，dtb 才是"SD 控制器存不存在"的开关。**
> `dmesg | grep sdhci-tegra` 是判据：正常应有 `.3`（eMMC）+ `.0/.1`（SD）；只有 `.3` 就说明 dtb 不对。

## 5. 最终解法：给根分区补齐 4.9.299 的模块树

不动 eMMC 的引导链（cboot + dtb + 内核 + extlinux 全部保持原样），只往 TF 卡根分区装模块：

1. 下 BSP：`Jetson-210_Linux_R32.7.3_aarch64.tbz2`（**266.6 MB**，注意 t210 列，不是 t186）
2. 取 `Linux_for_Tegra/kernel/nvidia-l4t-kernel_4.9.299-tegra-32.7.3-20221122092935_arm64.deb`（30.5 MB）
3. 拆包：`.deb` 的载荷从 R32.7.x 起是 **`data.tar.zst`**（Python 标准库不认，交 Windows 自带 `tar.exe`/bsdtar）
4. 抽出 `lib/modules/4.9.299-tegra`：**675 个文件 / 75.2 MB**，664 个 `.ko` 的 `vermagic` 全是
   `4.9.299-tegra SMP preempt mod_unload modversions aarch64`
5. 另从 `nvidia-l4t-firmware` 包里取 `rtl8822_setting.bin`（`rtl8822ce.ko` 只依赖这一个固件文件，主体编在模块里）
6. 打包成 `firmware/jetson-4.9.299-modules.tar.gz`（**19.8 MB**，sha256 `9A5DCD3C…E339F`）
7. 传到板上（走网线 + PC 上的 `python -m http.server 8000`，见 E-45）→ `tar -xzf … -C /` → `chown -R root:root`

**结果（实测）**：`sudo modprobe rtl8822ce` 无报错，`wlan0` 出现
（`IPv6: ADDRCONF(NETDEV_UP): wlan0: link is not ready` 是未关联 AP 的正常提示，不是错误）。
**内核/模块错配到此解决。**

## 6. 但卡坏了（新出现的阻塞）

装完模块之后，TF 卡开始持续报：

```
mmcblk1: error -84 transferring data, sector 21623624, nr 1024 …
mmc1: Data CRC error
sdhci: ============ REGISTER DUMP (mmc1)============
```

报错位置从 `sector 21.6M` 一路退到 `4.3M`（越来越靠前），retry 无效 → **介质在恶化，不是文件系统问题**。
之前那次"USB 设备枚举超时（`usb 1-2.2: device descriptor read/64, error -110`）"也让 U 盘传不了文件，
但供电是 **DC 5V/4A**，所以那更像是 USB 控制器/线材，不是供电。

**结论：必须换卡。** 这也解释了为什么后来怎么改引导都"认不到卡"——前期是 dtb，后期是卡本身。

## 7. 经验（可复用）

1. **查 eMMC 版本要看 `boot/Image` 里的 `Linux version` 字符串**，不是看 rootfs 里的版本文件——BSP 骨架里什么都没有。
2. **`README.txt: Download and extract the sample filesystem…` 是"这是空壳 rootfs"的铁证**，见到它就说明 eMMC 只有引导 + 内核。
3. **内核版本对不对，`uname -r` vs `ls /lib/modules` 一句话判死；但"SD 认不认"由 dtb 决定**，判据是 `dmesg | grep sdhci-tegra` 里有没有 `.0/.1`。
4. **串口敲长命令必错**（E-37 的升级版）：一条命令里塞 `mkdir; mount; cp; sync; reboot`，只要一处漏字，后面的 `reboot -f` 照样执行，症状看起来像"改动没生效"，实际是命令没执行对。**长命令一律拆成短行，每行单独看回显。**
5. **initramfs 里没有 `sync`（也没有 `head`/`uname`）**，写盘后要用 **`umount` 收尾**再 `reboot -f`，否则缓存丢在内存里。
6. **官方不给 4.6.3 的 SD 镜像**，别在这上面浪费时间；要么亚博出厂镜像，要么自己从 BSP 抽模块（本文件第 5 节）。
7. **`.deb` 载荷可能是 `data.tar.zst`**（R32.7.x 起），Windows 上让 `tar.exe`（bsdtar）去解，别硬用 Python。
8. **判断"卡坏"和"配置错"要分开看**：`error -84 / Data CRC` 是介质层，`mmcblk1 不存在` 是设备树层，两者的修法完全不同。
