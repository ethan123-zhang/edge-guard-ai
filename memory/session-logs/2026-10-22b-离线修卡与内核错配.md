# 2026-10-22（晚）— 从"向导又挂了"到"板子能用"，以及一个更深的坑

> 流程已写进 `docs/04` §2.0 的「首启刮不起向导 / 报 debconf 锁」和「内核/模块版本错配」两节。
> 本文件只记今晚发生了什么、怎么走出来的、还欠什么。

## 1. 起点

重烧官方 JP46（`sd-blob-b01.img`）后首启，串口只有三行、按 Enter 无反应：

```
debconf: DbDriver "config": /var/cache/debconf/config.dat is locked by another process
System configuration setup wasn't completed. Please reboot device and try again.
```

用户第一反应是"镜像是不是坏了、要不要换镜像"。**不是。** 三条反驳证据：

1. 镜像校验过（zip CRC、`Content-Length`、SHA256、唯一 payload `sd-blob-b01.img`）；
2. 同一张镜像 10-21 已经走进过向导（EULA→键盘→时区→用户名→APP 分区）；
3. 这条报错是**运行中的 Ubuntu 里两个进程抢文件锁**，坏镜像到不了这一步；
4. 每次开机**一字不差**复现 → 逻辑问题，不是随机损坏；重烧也无效（这就是重烧后的结果）。

## 2. 真因（从卡里的单元文件读出来的）

```
/etc/systemd/system/default.target -> nv-oem-config.target
/lib/systemd/system/nv-oem-config-debconf@.service     ← 模板单元
```

- JP46 把**默认启动目标**设成 `nv-oem-config.target`；
- 该 target 会给 **tty1 和 ttyGS0 各实例化一份** `nv-oem-config-debconf@`；
- 先到的占住 `debconf` 锁、在**看不见的 tty1** 上 `no limit` 等人；后到的立刻报 lock 退出。

**这条改写了之前的结论**：10-21 得出的「EDID 坏 → 回退串口」只是**表象之一**，
真正的结构原因是默认目标写死成向导 target。

## 3. 走出来的路（可复用）

1. **U-Boot 单用户那条路走不通**（原计划）：micro-USB 的 `ttyGS0` 是系统起来后由 gadget 脚本创建的，
   U-Boot 控制台在调试 UART（J50），没有 TTL 线就够不到。
2. **离线改卡**（最终采用）：读卡器 → `usbipd` 直通 WSL2 → 挂 ext4 → 建账号/关向导/放开串口 getty。
   写成脚本：`scripts/jetson-offline-unlock.ps1`。
3. **两个卡住过的语法坑**（都已修，记在这里省下一次）：
   - `usbipd` 5.x：`-w/--wsl` **直接跟发行版名**，没有 `--distribution`；
   - 本机默认 WSL 发行版是 **docker-desktop** → 所有 `wsl` 调用必须显式 `-d Ubuntu-22.04`；
   - `wslpath` 会把 `C:\…` 的反斜杠吃掉 → 自己做 `C:\x → /mnt/c/x` 映射。
4. **串口接管**：SSH/HDMI 都不可用时，用 .NET `SerialPort` 直接读写 COM16（115200 8N1 流控 None），
   写成 `scripts/jetson-serial.ps1`。**注意串口会偶发丢字符**，一旦丢了引号 bash 就卡在 `>` 续行；
   所以标记行别用引号，命令尽量短。

## 5. 发现的更深的坑（未解决）

**内核/模块版本错配**：`uname -r` = 4.9.299-tegra，`/lib/modules` 只有 4.9.253-tegra。

- 亚博把引导配置写进 **eMMC**（`/boot/extlinux/extlinux.conf`，`APPEND … root=/dev/mmcblk1p1`），
  于是引导器加载 **eMMC 的 4.9.299 内核 + 厂商 dtb**，根分区却是 **SD 卡上的官方 JP46**；
- eMMC 的 APP 只有 171MB 骨架，**没有模块树可捞**；
- 后果：所有 out-of-tree 模块失效 → **`wlan0` 不存在**（RTL8822CE 是模块，`lspci` 能看到卡）、
  `nvzramconfig`/`nvpmodel`/`systemd-modules-load` 全 `[FAILED]`。内建驱动正常，所以系统能跑。

**结论**：在这块板上，**官方镜像"完整运行"的前提是先处理掉 eMMC 的引导配置**。这是买板时不知道的事。

## 6. 卡在哪 & 下次开工第一件事

**卡点：板子没有出口（internet）**，因此 `apt`、OpenCV 源码、pip 全都做不了。

- PC 与板子之间直连（`192.168.137.50` ↔ `192.168.137.1`）正常，ping 通、SSH 通；
- PC 那块有线网卡是 **Windows ICS** 的 `192.168.137.1`，但 NAT 不转发（板子 ping 不通 `223.5.5.5`）；
- 试过把 PC 的策略代理（`127.0.0.1:7752`）反推到板子：**隧道通了，但所有源都 403**
  （`archive.ubuntu.com` / `github.com` / `pypi.org` / `developer.download.nvidia.com` 全部被策略拦）；
- 所以必须要一个真出口，二选一：**① 网线插到路由器 LAN 口**（最省事，DHCP 直接上网）；
  **② 管理员 PowerShell 跑 `Restart-Service SharedAccess`** 修 ICS。

**下次开工顺序**：
1. 解决出口（上面二选一）→ 板子 `ping 223.5.5.5` / `getent hosts www.baidu.com`；
2. `apt-get update && apt-get install -y build-essential cmake git python3-dev python3-numpy`；
3. **编 OpenCV 4.5.4（先不带 CUDA）**：40–60 分钟就能拿到 `cv2.FaceDetectorYN`，先回答 V1 的
   "能不能跑通 + 单帧耗时"；CUDA 版（`-DCUDA_ARCH_BIN=5.3`，预计 4–6 小时）留到确认 CPU 版太慢再上；
4. 跑 `scripts/jetson_baseline_probe.py` 拿基线数字（答辩要用）；
5. WiFi 单独排期：走 `docs/04` §2.0「内核/模块错配」的三条出路。

## 7. 型号口径纠正（**2026-10-23 用户确认**）

昨晚据"板上有 eMMC"推断这块是**亚博 SUB 版**，**错了**。用户确认：**就是 Jetson Nano B01**（模块 `p3448-0002`）。
B01 模块本身就带 eMMC（实测 14.7 GiB）+ 载板 TF 卡槽，"两个都有"是正常形态。

影响：

- **不走 SUB 的那套流程**（U 盘镜像 + `flash.sh -r jetson-nano-devkit-emmc` 写 eMMC 引导）——那是 SUB 板的；
- 本板走 **NVIDIA 官方 SD 卡镜像**这一套（本来就在用）；
- 但**内核/模块错配的问题不变**：eMMC 里是厂商内核 `4.9.299`，TF 卡上是官方 JP46 的模块 `4.9.253`。
  要 WiFi 就得让版本一致 —— ① 换亚博出厂镜像（模块是 4.9.299，最省事）；② 把 eMMC 的引导内核换成官方 4.9.253（有砖风险）。

教训：**型号以用户/官方规格为准，不要从"有没有 eMMC"倒推板型。**
